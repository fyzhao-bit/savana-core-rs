\begin{abstract}
Tool-using language-model agents interpret attacker-controlled content while
proposing actions under a user's credentials. Even if an agent sees only trusted
context, an arbitrary planner output is not evidence that the user authorized
its choice. \sys{} binds monitored requests to a separately authenticated,
bounded task contract. The kernel checks complete action alternatives rather
than independent field allowlists, records seven non-authoritative control
selections, and produces action-scoped endorsements only from checked evidence
within that contract. Task accounting, approvals and dispatch commitments are
consumed atomically, so replanning and fresh identifiers do not reset authority.
The executor checks the actual application request before a provider attempt
and verifies completion from the retained response. Existing information-flow
and declassification gates remain mandatory. We implement this path in the Rust
runtime and client integration. Native fixtures exercise dependent multi-step
execution, malicious workers, lost acknowledgements and executor recovery;
a separate bounded oracle checks task accounting. These are engineering
witnesses, not empirical attack-success or performance results. The prototype
supports closed request profiles and structured authorization; it does not claim
general natural-language intent inference, provider-internal semantics, or
complete crash availability.
\end{abstract}

\section{Introduction}
\label{sec:intro}

An agent can have permission to use a tool without having permission to use it
for the current task. Suppose Alice asks an assistant to summarize report A.
Bob is a permitted reader, and installation policy allows the mail connector.
A compromised planner chooses to send the report to Bob. Neither an acceptable
destination nor an available connector establishes that this task authorized
a send. This is an authority-origin problem, not necessarily an illegal
confidentiality flow.

A second failure arises even when a task explicitly permits sending. Consider
a contract allowing $(A,\mathrm{Alice})$ and $(B,\mathrm{Bob})$.
Separate resource and recipient allowlists also accept $(A,\mathrm{Bob})$.
A third failure is temporal: a permitted action may be repeated under fresh
identifiers, or a dependent successor may be started after an unverified
success claim. Finally, checking a planner's description is insufficient if
a downstream worker changes the request actually transmitted.

These problems persist under our threat model even if prompt-injection
detection is perfect: we allow arbitrary planner outputs, including outputs
derived from trusted context. \sys{} does not infer authority from context
cleanliness or model confidence. This is an assumption about the component
we confine, not a claim that every model or competing architecture is vulnerable
to every example.

Reference monitors, capabilities and information-flow control provide the
foundations for separating computation from authority~\cite{saltzer1975,
dennis1966,denning1976,myers1997}. Agent systems already apply these ideas.
CaMeL separates control and data flows and checks capabilities at tool
calls~\cite{debenedetti2025camel}; Fides studies planner expressiveness under
confidentiality and integrity tracking~\cite{costa2025fides}.
Progent checks tool arguments and distinguishes policy narrowing from approved
expansion~\cite{shi2025progent}. PCAS and its revised FORGE formulation enforce
policies over execution context and causal history~\cite{palumbo2026pcas,
palumbo2026forge}. Task-scoped authority is also central to IGAC and
CapAgent~\cite{zhu2026igac,hou2026capagent}. We do not claim to introduce these
general concepts.

Our focus is the \emph{implementation continuity} of task authority: the same
bounded relation and task state must govern the proposal, its approval,
the durable reservation, the request emitted by the executor, and the
completion evidence used by subsequent actions. A signature at only one
boundary does not establish continuity at the others.

\sys{} introduces a task contract before planning. It groups complete
alternatives into stable clauses with magnitude limits, attempt budgets
and success dependencies. The model may generate new plans within this
scope; a plan is not itself an authority root. Each proposal is matched against
the current relation and state. Seven typed control records retain the
proposer's untrusted status. Checked endorsements are separate authority
evidence, not more-trusted data derived from model output. Action approval
can select an allowed action but cannot add a resource, recipient or effect
outside the contract.

The kernel derives a closed business request from owned values and an
authenticated descriptor profile. A content commitment precedes approval;
a later authorization commitment binds all required endorsements and the
atomic task transition. The executor compares the worker's actual request,
target and credential identity before opening the provider-attempt boundary.
The retained response, interpreted by a reviewed codec, determines whether
a successor's success dependency is satisfied.

\paragraph{Contributions.}
First, we give a bounded task-trace design combining complete action relations,
separate endorsement and durable consumption
(\S\ref{sec:contract}--\S\ref{sec:durable}).
Second, we implement continuity checks from authenticated issuance through
actual requests and verified outcomes in the existing Rust runtime
(\S\ref{sec:boundary}--\S\ref{sec:implementation}).
Third, we provide implementation witnesses and a bounded differential
accounting model, separating them from the empirical experiments still required
(\S\ref{sec:evidence}--\S\ref{sec:evaluation}).
The contribution is neither a more expressive general policy language nor a
claim that prior systems cannot express an equivalent relation.

\section{Threat Model and Scope}
\label{sec:threat}

The adversary may control retrieved content, tool results, all planner outputs,
the agent process and a connector codec worker. It knows the policy, can
choose messages allowed to the agent role, and can schedule crashes and message
loss. Its objective is a monitored request outside the current authenticated
task relation or remaining state constraints. Choosing an undesirable action
inside an overbroad contract is a separate policy-fidelity problem.

The trusted computing base (TCB) comprises the authenticated input boundary,
task issuer, approval service and renderer, profile publisher,
kernel policy/data owners, executor supervisor and provider transport,
deployment identity/key selection, cryptographic primitives and OS isolation.
It is distributed across services, not just a small Rust policy module.
A worker signature identifies a transcript, not its honesty; the supervisor
must still validate its meaning.

We assume adversaries cannot obtain trusted signing keys, alter trusted process
memory, defeat configured OS isolation, or roll back a correctly deployed trusted
state anchor. Root, kernel/hypervisor compromise and malicious administrative
policy are excluded. Test anchors do not establish this hardware assumption.

The guarantee concerns the \emph{monitored application request and attempt}.
A reviewed profile must faithfully identify the authority-relevant fields of
its supported operation, and the provider must implement its advertised semantics.
We do not prove that a provider maps a named file to the correct physical bytes
or performs no undocumented secondary effect. Authorized recipients may retain
or misuse received data. Timing, traffic, availability and covert channels are
outside scope.

\paragraph{Protected data is not invisible data.}
The agent receives representations explicitly released by the kernel, including
authorized masked or public views. It has no general right to raw vault contents
or arbitrary tool credentials. Masking accuracy is not a semantic confidentiality
theorem: missed text, permitted abstract information and authorized recipients
require separate analysis.

\section{A Bounded Task Contract}
\label{sec:contract}

The signed contract binds authorization identity, authenticated principal,
durable task, revision, installation, active manifest, validity interval,
user-evidence and rendering commitments, and bounded clauses. Implemented
source evidence is authenticated structured input or an independently approved
draft. An unsigned model-produced draft has no authority.

The wire format admits at most 64 clauses, 64 alternatives per clause and
32 predecessors per clause, subject to a 1 MiB encoded-contract limit.
Unknown versions/enumerations, ambiguous encodings, duplicate identities or
alternatives, invalid limits and cyclic/missing dependencies are rejected.
Quantities use checked bounded integers. These limits deliberately exclude
arbitrary executable policy callbacks.

\subsection{Whole alternatives, not independent sets}

For a clause $j$, let $R_j$ contain tuples
\[
  (t,c,e,r,d,p,u),
\]
where $t$ identifies the exact tool descriptor, $c$ the request profile,
$e$ the effect, $r$ the resource control, $d$ the destination control,
$p$ the parameter projection and $u$ the magnitude unit.
Action content supplies magnitude $m$ and binds payload, provenance, plan
revision, candidate-domain digest and pre-state digest/revision.
Matching requires membership of the \emph{entire tuple} in $R_j$, not independent
membership of fields in separate allowed sets.

Each clause specifies a positive per-action bound, total magnitude budget,
maximum attempts, predecessor identities and an explicit retry-after-proven-
no-effect flag. Consumption is shared across its alternatives. New plan steps,
request identifiers and runs cannot create new copies of this budget.

\subsection{Issuance and amendment}

The native issuer uses a deployment-selected, purpose-separated key.
Its private input proof binds finalized original input and the exact draft
to the authenticated principal, task and deployment. It validates the draft
against active signed business profiles and the caller's role before recording
pending issuance, then rechecks proof/profile context on installation.

Structured first issuance and approved-draft issuance are distinct.
An amendment names the existing authority/revision and requires task-purpose
approval; tool-purpose approval is insufficient. Durable installation retains
consumption and tombstones. Removing and reintroducing a clause or starting
another run does not erase charges. Revocation is a separate authenticated
operation that removes authority.

A general natural-language intent compiler is not implemented. Ambiguous prose
does not silently become an unrestricted read contract or a send grant.
The product can collect a bounded draft and obtain task approval. This makes
the boundary auditable, but adds authoring and approval costs to measure.

\subsection{Dynamic plans and complete domains}

Plans may change as results arrive. Preparation and commitment require current
authority; each action binds the plan revision actually evaluated. A fresh plan
permits fresh matching, not fresh authority. Stale matches cannot survive changes
to state, contract or relevant deployment identity.

The only implemented completeness source is the \emph{entire signed bounded
contract}. The candidate-domain commitment includes contract digest, revision,
clause identity, alternative count and canonical contract bytes. Search pages,
runtime values and caller-selected subsets do not prove completeness. We do not
infer complete domains from an open registry or the external world.

Singleton endorsement requires one complete alternative and exactly one allowed
positive magnitude. Finding one convenient value does not prove uniqueness.
Even a genuine singleton does not make the model selection trusted data:
authority evidence remains separate.

\section{Control Evidence Without Trust Laundering}
\label{sec:endorsement}

Data provenance and control evidence have different jobs. Provenance tracks
representations and their reader/effect constraints. Control evidence establishes
why this exact request is authorized now. A trusted input cannot make an
arbitrary model choice authoritative merely by appearing in its context.

For a verified whole-action match, the kernel creates seven typed selection
records. Each includes facet, selected projection, content digest and proposer
parent. All have external-untrusted integrity and a \READ{} ceiling, regardless
of candidate trust. These are \emph{separate control records}, not ordinary
derivation nodes with increased authority.

The checked endorsement constructor accepts only evidence within the matched
contract: an explicit complete alternative, a verified complete-domain singleton,
or an expected-key verified action approval. It rechecks current state.
Endorsement fields are private. Ordinary value derivation cannot accept an
endorsement as a provenance parent; a compile-fail test checks this type boundary.
A match or endorsement is not a dispatch capability: the durable owner must
still check budgets, dependencies, freshness and all existing gates.

\subsection{Acyclic commitments}

The object approved by the user precedes the proof authorizing it:
\begin{align*}
  \CD &= H_{\mathrm{content}}(\mathrm{encode}(x)),\\
  E_i &= \mathrm{endorse}(\CD,i,\mathrm{evidence}_i),\\
  \AD &= H_{\mathrm{auth}}(\CD,E_1,\ldots,E_7,P,\Delta).
\end{align*}
Here \CD{} and \AD{} denote ContentDigest and AuthorizationDigest;
$x$ is bounded action content, $P$ policy identity and $\Delta$ the proposed
task transition. This notation summarizes typed canonical encodings, not a
substitute wire specification. Content contains no future endorsement or
settlement. Consent-requiring endorsements carry the verified settlement
identity/nonce, consumed consistently with the action at atomic prepare.

All seven endorsements occur exactly once in canonical order and refer to the
same content, proposer, contract/domain and state. Independent literal digest
vectors and field mutations check these bindings. A request capsule's preseal
commitment binds content and canonical business request; the dispatch core
then binds this commitment and \AD. Sealing follows durable preparation,
avoiding a circular dependency on ciphertext that does not yet exist.

\subsection{Two approvals with different authority}

Task approval authorizes or amends a relation. Action approval consents to
one exact action within it. The latter cannot rescue a send outside a
summary-only contract or approve $(A,\mathrm{Bob})$ when only
$(A,\mathrm{Alice})$ and $(B,\mathrm{Bob})$ were authorized.

For a consent-requiring action, approvald signs the existing settlement and a
separately purpose-bound TaskActionApproval after verified user ceremony.
The native consumer verifies expected keys and exact task/content/context
before consuming consent. A generic approval is not rebranded by attaching an
arbitrary content digest; restore rejects a missing/substituted required proof.

The trusted display comes from canonical kernel content, not model prose.
It exposes resource/destination pairs, tool/effect, quantities, budgets,
prerequisites and exact request values alongside identities. Markup and misleading
format characters are escaped. Oversized safe expansion is refused rather than
truncated. This establishes display/content consistency, not user comprehension
or resistance to all phishing.

\section{Durable Task-Trace Accounting}
\label{sec:durable}

The policy owner serializes admission and persists task state in the existing
encrypted, rollback-protected snapshot. It does not add a second independent
task database whose updates could race the dispatch ledger. Before returning a
prepared dispatch, the owner rechecks the current contract, whole-action match,
endorsement set, required approval, state version, budgets and predecessors.
It commits their consumption and the dispatch binding in one snapshot.

Let $a_j$ be permanent attempts and $b_j$ charged magnitude for clause $j$.
For a new action of magnitude $m$, admission requires
\[
 a_j+1\leq N_j,\qquad b_j+m\leq B_j,\qquad 0<m\leq M_j,
\]
as well as known success for every required predecessor. Addition is checked
before mutation. The atomic reservation sets $(a_j,b_j)$ to
$(a_j+1,b_j+m)$ and records the exact nonce/core/authorization association.
Concurrent proposals against the same pre-state cannot both consume its last
slot: the second must re-evaluate current state or fail.

\subsection{Outcomes are authority-relevant state}

A success-dependent successor cannot rely on an agent message, dispatch ACK,
or unverified worker completion. Only exact, expected-key signed terminal
evidence can install a known outcome. Task completion epochs distinguish stale
matches even if an apparent state value is revisited.

A new retry after proven no effect is therefore not free: it consumes another
attempt, and requires current matching. Amendments cannot retroactively convert
old unknown outcomes into refundable no-effect results. Removed clause identities
retain consumption, and a new run never reissues the root contract implicitly.

\subsection{Uncertainty is not permission to resend}

The native owner reserves a query handle before any charge and records its exact
dispatch association before transport. If the executor receives the dispatch but
the reply is lost, retrying the same ticket returns the existing handle, rather
than minting another nonce or spending the budget again. The executor journal
distinguishes preparation, provider attempt, retained response and terminal state.
Recovery with a retained response decodes it without another provider call.

Verified terminal success may be the first evidence seen after prepare, if an
earlier effect-start acknowledgement was lost. The policy owner reconciles the
intent's intermediate and terminal stages in the same committed snapshot.
It does not invent an effect-start receipt or loosen ordinary transitions.

Tool-result bytes and the verified task outcome are committed before the native
owner sends the cleanup ACK. The owner records its terminal observation first:
if the ACK was processed but its response was lost, the next query still returns
the committed success. Final release follows the same observation-before-ACK
rule. A never-delivered ACK can leave executor artifacts retained; an autonomous
cleanup retry queue is not implemented.

These mechanisms do not establish distributed exactly-once effects.
An unknown external outcome remains unknown. Full kerneld restart preserves
durable authority/accounting but does not reconstruct all opaque execution or
session query handles. Such work may require workflow recovery; it does not
receive a reset budget. We distinguish this availability limitation from the
tested executor-journal reopen and authenticated authority recovery.

\section{Checking the Actual Execution Boundary}
\label{sec:boundary}

An approved description is useful only if it constrains what leaves the system.
The kernel and executor share a bounded business-codec specification, while
the executor independently checks the untrusted worker's output against it.
Shared interpretation avoids silently disagreeing parsers; it also makes that
specification and implementation part of the TCB rather than independent proofs.

\subsection{Signed profiles and exact routing}

A signed tool descriptor carries a reviewed business profile: codec/version,
operation name, typed field roles, effect and magnitude mapping, target identity
and credential identity. The initial codecs are a closed JSON-RPC 2.0
\code{tools/call} body and a reviewed fixed-POST body. Parsing rejects duplicate
keys before map conversion, unknown control fields, mismatched identifiers,
unsupported types, malformed Unicode and unbounded input. There is no generic
raw-byte fallback for unsupported new task-bound requests.

New tool dispatch resolves exactly one active registered connector through the
exact signed tool descriptor. The descriptor's provider identity must equal
the connector ID, which includes its registration identity, not merely a
business recipient. The profile's target must match the actual HTTPS URL and
TLS pin. A missing, inactive, removed, renamed or ambiguous route fails closed.
Both native prepare and executor dispatch/recovery check this route; registry
guards and core bindings prevent substituting a different head at execution.
Historical routing remains a compatibility path, not authority to upgrade a
legacy action into a new task-bound effect.

\subsection{Pre-provider checks}

The sealed capsule contains action content and the canonical request. Its
commitment is bound into the authenticated dispatch core alongside \AD.
The worker may parse/encode this material, but cannot choose an alternative
recipient, resource, operation, target or credential by emitting a validly signed
different request.

Before a provider attempt, the supervisor verifies the worker transcript and
compares its request against the kernel-bound canonical request. The transport
checks the target and credential slot. Authentication insertion is confined to
that slot/target; worker-provided authorization overrides or redirects are not
accepted. The final application-request digest is journaled with its
authorization before the provider call, and the actual response is retained.

The current wire transport remains a custom eleven-field CBOR application
frame over mutually authenticated TLS. The JSON-RPC or fixed-POST representation
is its logical business body. This is \emph{not} a claim that the prototype can
connect directly to arbitrary HTTP or MCP servers. It binds application-level
request content and routing, not literal TLS record bytes or remote internal
semantics.

\subsection{Completion and result ownership}

The transport-retained response is classified using the pinned response codec.
Malformed, mismatched-ID, explicit-failure and unknown responses cannot become
known success merely because a worker claims completion. Signed terminal
evidence binds the authorization, journaled application request, retained response
and completion descriptor. The native owner verifies these before committing
result data or advancing a success dependency.

Result digest and length use the protocol's canonical descriptor rather than a
separately invented local hash. Each verified tool result receives a
domain-separated vault identity bound to installation, task, run and commit.
Thus several results can coexist with immutable original input. Replaying the
same result is idempotent; substituting bytes for the same commit is refused.
Stable receipt time, rather than query time, supplies result provenance on retry.
This insertion is a trusted kernel data-plane operation, not an agent-facing
alternative ingress path.

\subsection{Final release is also an action}

Final release requires current task matching and both the applicable generic
consent and exact task-action proof. The existing leak gate inspects raw vault
plaintext before base64 encoding; transport encoding is not a way to evade it.
The closed request binds the original input identity and an application-turn
identity reserved by the receiver before planning.

The receiver checks this turn against its durable reservation and acknowledges
success only after durable claim. An old claimed record may be reconciled, but
does not authorize a new unbound legacy delivery. The implemented native producer
releases the owned original document, at most 32 KiB. Arbitrary synthesized agent
answers are not supported by this producer and are not claimed as implemented.

\section{Runtime and Client Integration}
\label{sec:implementation}

\sys{} extends existing Rust services rather than introducing a parallel
demonstration monitor. Authenticated ingress supplies original input; kerneld
owns task authority, policy, provenance and the vault; approvald verifies user
ceremonies; execd supervises workers and external attempts. The agent and its
model remain proposers. Typed, authenticated service protocols and opaque handles
separate application workflows from authority-bearing internal operations.

The existing G1/G2 input gates, G3 label/provenance checks, G4 stored semantic
binding, G5 validation, G6 consent and G7 dispatch/reconciliation remain in use.
The seven control facets in Table~\ref{tab:facets} are an additional representation
of an action, not new names for those seven gates.

Ordinary derivation does not improve integrity or expand reader/effect sets.
Existing signed-policy declassification mediates five representation changes:
agent view, planner envelope, approval display, executor handoff and final
release. Applicable exact-recipient and outgoing-byte checks remain mandatory.
Control endorsement cannot substitute for this data-flow authorization.
Conversely, an admissible data flow cannot substitute for task-effect authority.

The Rust client and asynchronous Python facade transport bounded drafts,
opaque handles and closed status observations. They do not sign contracts or
construct trusted evidence. The fixed browser editor obtains authenticated task
context, constructs complete alternatives and budgets, and invokes independent
task approval. Fresh authenticated recovery discovers existing pending requests
without uploading a new original or minting new authority.

The OpenClaw integration reserves a receiver turn before input, scope collection,
task approval and planning. Its private broker's \code{task.draft} exchange
returns data only; Rust builds the draft against authenticated context.
Invalid, refused or pending scope does not proceed to planning/release.
The host product still must implement that broker exchange. Plugin/SDK component
tests and a real receiver transport test do not demonstrate a live
browser-to-hardware-to-provider product session.

Production profile generation is also deliberately narrow. The development
materializer derives the supported final-release profile from actual generated
target, TLS and credential identities, verifies retained signed descriptors and
rejects placeholder/unreviewed inputs. We tested the generator but did not install
its output or migrate a running deployment. Unsupported report descriptors do
not acquire fabricated semantic mappings.

\section{Conditional Security Argument}
\label{sec:argument}

We state the intended abstract monitor property separately from implementation
evidence. Let a trace consist of contract revisions, reservations, monitored
provider attempts and verified outcomes. Given a correctly authenticated contract
and sound profile, its legal prefixes are those obtained by the checks in
\S\ref{sec:contract}--\S\ref{sec:boundary}. The monitored attempt projection must
remain a prefix of this permitted relation/state machine.

The argument has three obligations. \emph{Authority origin:} only authenticated
issuance or task-purpose approval installs a contract; arbitrary planner output
and action approval cannot enlarge it. \emph{State preservation:} the durable
owner's single transition checks complete membership, current evidence and
remaining counters before consuming an attempt. Exact replay preserves the
reservation; verified no-effect settlement refunds magnitude at most once;
only known success satisfies a predecessor. \emph{Boundary preservation:} a
provider attempt requires a verified dispatch and an actual request equal to its
bound request, while outcome authority comes from the retained response.

Under these assumptions, induction over abstract transitions preserves the
relation and budget invariants. This is a proof sketch for the stated monitor
abstraction, \emph{not} a machine-checked refinement proof of the Rust code,
cryptography, distributed transport, OS or provider. Tests exercise the
obligations but do not prove the assumptions or all possible interleavings.

The property permits adversarial choices already allowed by the contract.
It does not recover the user's unstated intentions, guarantee useful task
completion, or prevent disclosure through information intentionally released to
an authorized reader. Classical checked endorsement and robust integrity inform
our separation of evidence, but their language-level theorems do not
automatically transfer to this implementation~\cite{askarov2011}.

\section{Engineering Evidence}
\label{sec:evidence}

This section reports executable witnesses from the implementation snapshot,
not research benchmark results. The claim-to-code map and full verification
record accompany the source.

\subsection{Native integration fixtures}

The tool fixture drives authenticated input-owner validation, native task
issuance, actual planner prepare/commit, proposal and policy evaluation, atomic
prepare, signed/encrypted Suite1 IPC, the real executor protocol service and effect
gate, encrypted journals, worker-frame verification, response classification,
vault result commit and completion ACK.

Its nine cases cover an exact registered request, a missing route, a signed
worker changing the recipient, provider failure, lost dispatch ACK plus executor
reopen, renamed and duplicate routes, a dependent two-step task with replanning,
and a processed completion ACK whose response is lost.
Rejected pre-provider mutations have zero observed provider attempts.
The admitted cases have the asserted exact attempt count, including one after
dispatch/ACK uncertainty. These are assertions for selected traces, not an
attack-success rate over a population.

In the two-step case, step 2 is refused before step 1 succeeds. After verified
step-1 completion, a new plan can execute step 2. Replanning again cannot reset
either clause's one-attempt budget. Both tool results remain available as distinct
vault records. The final-release fixture adds seven cases covering exact delivery,
changed turn, failure, unknown outcome and both acknowledgement-loss boundaries.

The provider and worker are controlled in-memory fixtures. Encoding, signing,
verification, owner transitions and encrypted file reopen are real. Authentication
and approval proofs are test fixtures; they are not a live user hardware ceremony.
Compare-and-advance rollback anchors are in memory, not hardware. Separate suites
check real approval-service ceremony logic, local mTLS receiver behavior and
OS worker isolation. We do not concatenate these into an unperformed full-product
experiment. Fixture features are absent from production defaults and the new
executor fixture is forbidden in non-debug builds.

\subsection{Bounded differential exploration}

A separate accounting oracle explores 1,440 two-attempt traces with two clauses,
two complete alternatives, an invalid tuple, five first-outcome states, three
encrypted-owner reopen positions, stale/current matches and reused/fresh approval
nonces. It compares actual Rust admission and counters against the oracle,
including exact terminal replay. The run observes 984 admitted probes,
1,896 refused probes and six distinct accounting observations.

These counts describe a finite accounting projection, not exhaustive state-space
coverage of the protocol. Existing fault hooks separately test uncertain
issuance/prepare commit, durable rename boundaries, stale revisions, concurrent
prepares and refunds. Unbounded scheduling and full-kernel refinement are future
verification work.

\subsection{Regression scope and limitations}

The native feature-enabled library passes 316 tests; the protocol suite passes
248; the policy library passes 232. Python SDK/bridge/runtime/receiver tests
pass 61 cases and the TypeScript plugin passes 65. Counts are reported separately
to avoid double-counting test subprocesses and overlapping suites.

The default workspace run passed. Feature coverage combines a passed complete
attack matrix, including its five-minute replay boundary, with a successful
sequential feature-workspace rerun that omitted only that already-passed case.
One launchd-provided-socket test remains ignored for its platform prerequisite.
The verification record retains failed earlier runs: a shared test deadline
was made per-operation, and concurrent build configurations had overwritten a
shared test binary. No production timeout or security check was relaxed.

Integration exposed concrete mismatches that unit boundaries had missed:
business destination versus connector routing identity, schema-specific attempt
encoding, duplicated result-hash domains, terminal-first intent reconciliation,
single-input vault identity reused for later results, and ACK-loss observation
ordering. Fixes retain legacy wire encodings and recovery-only semantics where
required. They are not evidence of a previously missing planner whitelist:
committed-plan validation already existed and was retained.

\section{Empirical Evaluation Plan}
\label{sec:evaluation}

\textbf{Status: the experiments in this section have not been run.}
We report no empirical attack-success, benign-utility, approval-burden or latency
result. The engineering counts in \S\ref{sec:evidence} are not substitutes for
these measurements. This section specifies the evidence needed for a submission.

\subsection{Research questions and task corpus}

RQ1 asks whether complete task-trace enforcement reduces unauthorized
\emph{executed} requests under arbitrary planner/worker output. RQ2 asks how much
benign utility survives bounded contracts and fail-closed uncertainty. RQ3 asks
which boundary contributes protection beyond an equivalent static policy.
RQ4 measures mediation and recovery costs, including authority authoring.

Tasks should include summary-only requests, correlated multi-recipient delivery,
dependent read/modify/send workflows, budgeted repeated actions and receiver-bound
final release. Each must have an independently annotated intended relation and
permitted trace, not ground truth generated by the policy under test.
Adapt suitable tasks from AgentDojo~\cite{debenedetti2024agentdojo}, recording
unsupported schemas as unsupported rather than silently replacing their semantics.
Closed-profile synthetic tasks should be reported separately from adapted tasks
and live service tasks.

For each task, pair benign executions with adversarial variants at distinct
boundaries: retrieved-text injection; an arbitrary planner reply despite trusted
context; malicious agent API sequences; worker request substitution; forged
success over a retained failure/unknown response; concurrent budget exhaustion;
and loss/crash before and after each identified durable/effect boundary.
Report the number of tasks, runs, attacks and attempted effects separately.
Do not use multiple correlated probes of one task as independent tasks.

\subsection{Authority fidelity and human cost}

Let $I$ denote the independently annotated user-intended relation and $C$ the
installed contract. Report overgrant and undergrant between $C$ and $I$ separately
from enforcement of $C$. Otherwise a perfect reference contract can make a monitor
look secure while hiding an unusable or unsafe contract-creation process.
Evaluate reference-authored structured contracts and user-reviewed drafts as
separate conditions. General text compilation must not appear as an implemented
condition unless a compiler is actually added and evaluated.

Action-consent experiments need a stated decision policy. Do not grant every
attack request merely to force execution, or approve only benign requests using
an unreported oracle. Count task-creation approvals, amendments, action approvals,
recovery prompts, denials, timeouts and authoring corrections. A later user study
would need an appropriate ethics review; no such study is claimed here.

\subsection{Baselines and ablations}

Use reproducible versions of prompt-only execution, static connector/argument
policy, and applicable published task-policy/IFC systems. Match tool semantics,
source data, authorized destinations and intent inputs where possible.
For CaMeL/Fides, distinguish their intended planner assumptions from the stronger
arbitrary-planner experiment; do not label an out-of-model adversary an in-model
break. For Progent, PCAS/FORGE, IGAC and CapAgent, preserve supported update,
approval and trace policies rather than implementing weakened lookalikes.
Where faithful porting is infeasible, report a clearly named mechanism baseline,
not a numerical claim about the original system.

\subsection{Metrics and reproducibility}

Report attempted and completed unsafe actions, authorized task completion,
false blocking, quarantine and unresolved outcomes. Separate contract overgrant
from unsafe execution and separate blocking before a provider attempt from
failure after one. Give denominators and uncertainty intervals, grouping repeated
runs by task. Archive exact model/version, decoding settings, random seeds,
contracts, profiles, attack inputs, per-stage outcomes and exclusion rules.

Measure median and tail latency by stage: context/issuance, matching,
endorsement/display, durable prepare, request validation, completion and recovery.
Separate cryptography, storage synchronization, network/model time and human
waiting. Include the number of alternatives, clauses, retained records and
concurrent tasks. Recovery experiments must count both unsafe effects and
unresolved work; conservative blocking is a safety/availability tradeoff.
No placeholder number should be promoted into the abstract or conclusion.

\section{Related Work}
\label{sec:related}

\paragraph{IFC and endorsement.}
Lattice-based and decentralized IFC separate permitted information flows from
computation~\cite{denning1976,myers1997}. Checked endorsement addresses deliberate
integrity relaxation~\cite{askarov2011}. \sys{} uses these concepts rather than
claiming a new endorsement primitive. Its contribution is the typed,
task-state-bound application of endorsement to an execution pipeline. It does
not inherit a language-level noninterference or robust-integrity theorem by
using similar terminology.

\paragraph{Agent control and policy.}
CaMeL extracts control/data flows from a trusted query and enforces capability
policies at tools~\cite{debenedetti2025camel}. Fides formalizes planner
expressiveness under dynamic taint tracking and provides selective-hiding
primitives~\cite{costa2025fides}. Our task-root check is complementary to data-flow
confinement: a permissible flow alone does not establish that the task requested
the effect. This observation is not an experimentally demonstrated bypass of
either system.

Progent's revised design uses symbolic tool/argument policies, with solver-checked
narrowing and explicit approval for expansion~\cite{shi2025progent}.
PCAS uses a dependency graph and Datalog-derived policies; the later FORGE
formulation makes observability assumptions explicit~\cite{palumbo2026pcas,
palumbo2026forge}. These works already address policy evolution and temporal
context. We instead examine concrete preservation of bounded task accounting
and exact request/response evidence across durable owners and an untrusted worker.
We do not claim temporal policies are unique to \sys{}.

\paragraph{Intent-scoped capabilities.}
IGAC derives a short-lived intent certificate, narrows static tool authority and
checks tool/payload effects. It explicitly identifies certificate fidelity and
sound effect bounds as conditions for request confinement~\cite{zhu2026igac}.
CapAgent maps human-attested intent to purpose-bound capabilities and combines
scope checks with semantic data-flow governance~\cite{hou2026capagent}.
These are close prior work, so signed task intent is not our novelty claim.
\sys{} deliberately offers a narrower closed-codec semantic boundary while
making joint alternatives, separate control evidence, atomic consumption,
actual-request validation and retained-outcome reconciliation explicit.
Comparative security or performance superiority remains unmeasured.

\section{Limitations and Next Verification Steps}
\label{sec:limits}

The strongest unresolved research question is not whether more tests pass,
but whether the implementation can be shown to refine a precise trace
specification under all relevant interleavings. The bounded accounting oracle
does not model every distributed failure, parser, credential or platform.
A next step is a small explicit-state model of issuance, approval, prepare,
attempt, outcome and recovery, with a stated mapping to each durable owner.
Mechanized refinement or targeted model checking must identify its bounds and
assumptions rather than being described as a proof of the entire product.

Contract authoring remains a trust/utility boundary. Broad user approval can
authorize undesirable choices, while exact alternatives can reject legitimate
unanticipated work. Current profiles require manual review and do not cover
arbitrary MCP schemas. Extending them introduces semantic and TCB obligations,
not merely additional parsing code.

Full kernel-session recovery, autonomous cleanup of never-delivered ACKs,
arbitrary synthesized final answers and a live hardware-backed browser/product
session are not established by this increment. Deployment signing, hardware
rollback protection and complete mediation must be verified for the actual
target platform. Source hashes detect changes; they do not certify a release
or prove that a manifest lists the entire TCB.

\section{Conclusion}

\sys{} confines a model's proposals using separately authenticated task authority,
complete action relations, state-bound endorsement and durable accounting.
The execution boundary checks the request actually attempted and the response
used as evidence for subsequent steps. The implementation and bounded witnesses
support these concrete mechanisms, with explicit recovery and codec limits.
Empirical security, utility, approval-cost and performance comparisons remain
necessary before drawing a publication-level effectiveness conclusion.

\section{Ethical Considerations}

The reported checks use controlled fixtures and local test services. No attack
against an uninvolved external service, real user study or production credential
change is part of this evidence. Future evaluation should use synthetic/private
test accounts, avoid collecting real secrets, and separate authorized testing
from live user workflows. Approval prompts are themselves a potential source of
confusion and burden; any participant study requires suitable consent and review.

\section{Open Science}

This working draft is not yet an artifact submission. The accompanying source
contains the runtime changes, closed codecs, native fixtures, bounded accounting
oracle, claim-to-code map and verification record with failures and exclusions.
Before submission, an anonymous, frozen artifact must include reproducible build
instructions, pinned dependencies and all measured experiment inputs/outputs.
No anonymous artifact URL or benchmark dataset is asserted to exist yet.

test-only keys must not be mistaken for production trust material.

\section{Illustrative Trace and Witness Boundary}

Consider two one-attempt clauses. Clause 1 permits $(A,\mathrm{Alice})$.
Clause 2 permits $(B,\mathrm{Bob})$ after known success of clause 1.
A proposal for clause 2 initially fails. A proposal for clause 1 reserves its
attempt and magnitude. A transport ACK alone does not enable clause 2; a verified
successful terminal response does. A new plan may then execute clause 2, while
another plan cannot replenish either budget. This ordering is exercised by the
native two-step fixture, not just by an isolated matcher.

If the first provider reply is unknown instead, the successor remains blocked.
If a worker changes Alice to another recipient, validation refuses the request
before any provider attempt. If the dispatch ACK is lost after success, the
original query identity remains and executor reopen reconciles the retained
response without sending again. These witnesses establish the stated cases
only; they do not demonstrate full kerneld-session restoration or all
provider-side failure behaviors.
