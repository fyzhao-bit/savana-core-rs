# 研究定位：不是又一种意图证书，而是任务授权的跨边界保持

日期：2026-09-05。生产代码基准：73e0684；本增量只增加研究模型、证据、CI 和论文。
这是“做 1 和 2”的第 1 项。第 2 项见[独立轨迹规格](task-trace-spec.md)。
以下是可审查的贡献定位，不是已证明的全球首创结论，也不是录用保证。

## 1. 收紧后的核心主张

给定独立认证的有界任务合同，即使提议者和工具 worker 给出任意输出，
受监控的应用请求仍必须对应同一份合同下的一次合法预留。
审批、并发预留、实际请求、后继依赖和恢复不能各自采用互不一致的授权事实。

研究对象不是“LLM 是否听话”，而是这些组件连接起来后，权限是否在某个边界被扩大。
要展示的是一组可审查的组合义务、有限模型中的反例和对应的 Rust 实现证据。
签名、IFC、capability、意图证书、时序策略、事务、幂等和 checked endorsement
本身都不是本论文新发明的机制。

可以主张的三项产物：

1. **独立的轨迹规格。** 用任务来源、历史消耗和外部请求/响应观察定义允许轨迹，
   不再用“通过 Savana 的检查”来定义什么是安全。
2. **组合失败的最小见证。** 在有限模型中，分别移除一项连接义务，得到违反该规格的最短轨迹。
   这说明相应义务有必要性，不说明只有 Savana 能实现它。
3. **实现对应和验证边界。** 指出这些义务由哪个 Rust owner、哪个提交点承担，
   并保留模型没有覆盖的 TCB、平台和恢复缺口。

“把已知机制放在一起”仍可能被审稿人认为贡献不足。模型检查提升了论证的明确性，
但不能代替同能力基线比较，也不能自动证明新颖性。

## 2. 最接近的工作：已有什么、应当怎样公平比较

公开文本未建立的实现性质记为待验证，不由缺少描述推断漏洞。

| 工作与原始来源 | 已有能力，不能冒领 | 对 Savana 的约束和公平比较要求 |
| --- | --- | --- |
| [CaMeL v2](https://arxiv.org/html/2503.18813v2)，§3、§5 | 从可信用户查询提取控制流，在解释器中追踪数据来源并按 capability 检查工具调用 | 保留其规划/数据隔离结构与信任前提。不能把任意恶意 planner 当成其默认攻击模型，再宣布绕过 |

| [Progent v3](https://arxiv.org/html/2504.11703v3)，§4–§6 | 工具/参数符号策略；SMT 区分权限收缩与需要审批的扩张 | 必须给它可表达联合元组的策略和等价任务范围；不能用错误配置的独立字段白名单代表 Progent |
| [FORGE v3](https://arxiv.org/html/2602.16708v3)，§3.4–§3.5、§5、附录 A | 因果图上的 Datalog 决策、可观测环境合同、条件性正确性论证和持久化实现 | 不能把“历史策略”“完整中介”或“持久化”当成独有。比较其环境合同由谁落实，尤其是原子预留和 worker 后的真实请求观察 |
| [IGAC v3](https://arxiv.org/html/2606.22916v3)，§II-D、§III、§IV | 意图证书、静态权限收缩、payload/effect 边界、preflight/state witness、幂等重放与分步工作流 | 不能说它只有静态权限或没有幂等。比较证书保真、effect contract 和跨 owner 故障语义；不假设其已验证 adapter 是恶意 worker |
| [CapAgent](https://doi.org/10.3390/bdcc10090293)，2026-09-01，§3–§6 | 人工确认的任务意图、目的绑定 capability、调用预算/nonce、委派收缩和语义数据流治理 | 与“意图到执行的绑定”高度重叠。Savana 应聚焦封闭 request codec、持久化消费及不确定结果处理，不能把 token 或调用预算当作新概念 |

FORGE v3 与较早的 [PCAS v1](https://arxiv.org/html/2602.16708v1)
是同一个 arXiv 条目的不同版本，不能算成两个相互独立的最新系统。
CapAgent 的完整页面直接访问失败，本轮通过出版方索引返回的正文片段核对了上述章节；
未据此推断其未展示的崩溃或并发实现性质。

当前差异假设是：**把联合动作关系、一次性证据、任务级原子记账、
worker 之后的真实请求以及经过验证的完成证据，落到一个明确的跨 owner 轨迹规格中。**
这是部署/实现的组合问题，不是声称其他策略语言无法表达这些条件。
若等价配置的已有系统已经落实所有义务，则应报告等价性，收缩贡献；
不能继续靠重新命名维持“独有性”。

## 3. 三个不依赖 Savana 实现的反例

这些是一般组合错误的数学见证，不是对上表系统的实际攻击。

**联合关系不能被投影集合替代。** 令允许关系
R = {(A, Alice), (B, Bob)}。A 属于资源投影，Bob 属于收件人投影，
但 (A, Bob) 不属于 R。因此每个字段都被允许，不蕴含整次动作被允许。
这不是新数学定理；它说明实验必须检查关系，而不能只检查字段覆盖率。

**逐次合法不蕴含整段轨迹合法。** 一个任务最多允许一次发送。
两个请求都在“已消费 0 次”的旧快照上通过检查，然后分别提交。
每次判断在其快照上成立，但最终轨迹包含两次消费。
解决义务是“检查与提交在同一个串行化点生效”，而不是再加一个签名。

**被批准的描述不蕴含实际请求相同。** 用户批准给 Alice 发 A；
下游 worker 把请求改成给 Bob 发 A。原审批仍可是真实且签名正确的。
若没有在持有传输权限的边界重新检查绑定，审批本身不能约束替换后的请求。

再加入崩溃后丢失尝试历史，或者把 worker 自报成功用作下一步的前置事实，
就分别得到重复尝试与伪造后继权限。这些都要在轨迹语义中排除。

## 4. 已实现的有限模型反例

实现：[模型与运行说明](../../verification/task_trace/README.md)。
原始输出：[results.json](../../verification/task_trace/results.json)。
每条为对应有限配置中 BFS 找到的最短违规前缀；事件数不能跨配置比较“攻击难度”。

| 故意削弱的义务 | 模型中的最短违规前缀（省略固定参数） | 违反规格 |
| --- | --- | --- |
| 把动作审批当成任务根 | action-purpose issue | S1：授权来源 |
| 联合关系换成字段笛卡尔积 | issue → approve(A, Bob) → reserve | S2：内容绑定 |
| 把检查与提交拆开 | issue → 两个旧快照 approval → 两次 reserve | S3：任务消耗 |
| 不检查审批 pre-state | issue → 两个 approval → reserve 1 → 使用旧 approval reserve 2 | S2：状态绑定 |
| 不检查实际请求 | issue → approve → reserve → fence(被替换的请求) | S2：真实请求 |
| 接受 worker 自报完成 | issue → approve → reserve → worker success | S5：完成证据 |
| 前置成功不检查语义 epoch | 第一步真实成功 → 修改合同语义 → 新审批 → 第二步 reserve | S4：依赖 |
| 尝试 fence 只在内存中 | issue → approve → reserve → fence → emit → crash → reopen → fence → emit | S6：同执行身份重复尝试 |
| unknown 返还量额度 | 预留并尝试 → 回复丢失 → unknown → settle/refund | S3：未知结果不能返额 |
| 修改合同清零历史消费 | issue → approve → reserve → amend/reset | S3：历史不丢失 |
| 完成提交前发 ACK | 预留 → 尝试 → retain → certify → ACK，尚未 settle | S7：结果提交顺序 |

故意削弱的版本只存在于研究模型的参数中，**没有修改或关闭生产内核的任何检查**。
这些结果不等于 prompt-injection benchmark，也不代表对已发表实现的攻击成功率。

## 5. 下一轮判断标准

第 1、2 项的可验收产物是：这份有版本来源的对比、独立规格、可重现的有限检查、
反例、正向见证和 Rust 对应表，以及同步收紧的论文。
没有同时完成未被选择的真实动态发现、更多生产 connector 或实证实验。

若要支持高接受论文，还需要：

- 用相同任务、工具能力、授权范围、预算和失败模型比较，而不是降低对方配置。
- 区分已有系统原实现、经过扩展的同能力实现和我们自制的机制消融。
- 测量合同的过授权/欠授权和用户审批负担；这里假设任务根正确并不能消除该问题。
- 审查完整中介、codec 语义、持久化和部署身份的外部假设；本模型没有证明它们。
