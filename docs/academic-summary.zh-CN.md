# Savana：把 Agent 动作绑定到用户授权的任务轨迹

更新日期：2026-09-05。代码基准：**73e0684**，分支 codex/intent-bound-execution。
本文取代 2026-09-03 的旧总结；旧版本仍可通过 Git 历史查看。

本轮完成的是已批准的有界研究实现和论文对齐，不是部署验收、形式化证明或论文实验。
“四分路线”是讨论中的质量目标，不代表审稿分数保证。
随后完成的第 1、2 项研究增量增加了独立轨迹规格、有限模型检查和源码对应表；
生产 Rust 内核仍保持上述基准，没有关闭安全检查。

## 1. 研究问题

模型即使只看到可信上下文，也不能因此获得替用户授权的资格。
例如，用户只让系统总结报告 A；Bob 本来有阅读权限，邮件工具也已安装，
仍不能推出“本次任务允许把 A 发给 Bob”。

另一个例子是任务允许“给 Alice 发 A”和“给 Bob 发 B”。
分别检查资源白名单与收件人白名单，会错误接受“给 Bob 发 A”。
正确的授权对象是完整动作组合，以及整个任务还允许执行的次数、量和顺序。

Savana 的研究重点是让这份授权约束贯穿：模型提议、可信审批、
持久化预留、执行器实际发出的请求，以及后续步骤使用的完成证据。
不是声称首次提出能力、信息流、意图证书或时序策略。

## 2. 当前实现

1. **先有任务授权，再让模型规划。** 内核接受经过认证的结构化输入，
   或独立审批过的草案。没有通用自然语言意图编译器；模型不能自己签发授权。
   修改任务范围需要任务级审批，单次动作审批不能扩大范围。
2. **匹配整个动作。** 有界条款包含完整工具、效果、资源、目的地、参数和量单位组合。
   本期候选完备性只来自完整签名合同，不来自搜索结果、局部集合或通用注册表推断。
3. **控制选择不洗白为可信数据。** 七个控制面是工具、效果、范围、量、参数、
   目的地和触发条件，均保留不可信/READ 上限。经检查的 endorsement 是独立证据，
   不能作为普通值派生的提权父节点。这七个控制面不是现有 G1–G7 策略门。
4. **审批前后的承诺不循环依赖。** ContentDigest 先固定审批对象；
   AuthorizationDigest 再绑定全部证据与任务状态转移。审批展示由内核内容生成，
   不用模型文案替代真实动作，过大内容拒绝而不是截掉重要部分。
5. **整个任务统一记账。** 任务消耗、审批消费与 dispatch 绑定在同一持久化事务中提交。
   换计划、run、nonce 或请求 ID 不重置预算。未知结果不解锁“前一步已成功”。
   经过验证且合同允许的无效果结果最多返还一次量额度，尝试次数不返还。
6. **执行器检查真实请求。** 新路径必须解析到唯一有效且与签名描述一致的 connector；
   执行器在 provider attempt 前检查 worker 生成的实际请求、目标与凭据身份。
   支持经过评审的封闭 JSON-RPC tools/call 与固定 POST 逻辑体。
   传输仍是 mTLS 上的十一字段 CBOR 帧，不是任意 HTTP/MCP 客户端。
7. **完成证据和结果不由模型自报。** 从保留的实际响应经受信任解释器得到终态。
   多步结果在 vault 中使用任务/run/commit 绑定的独立身份，不覆盖原始输入。
   重放同一结果幂等；同一 commit 替换内容被拒绝。
8. **通信丢回复不自动重发副作用。** 不确定 IPC 前先记录原查询身份；
   同一 ticket 重试不再次发送或收费。结果和任务终态提交后，
   先保留成功观察，再发送清理 ACK，避免 ACK 回复丢失抹掉成功。

原有标签、溯源、解密级、G1–G7、角色隔离、签名、配额和部署 fence 不被这些机制替代。
Python/客户端传递受限输入和不透明句柄，不承担可信证据签发。

## 3. 直接验证了什么

| 证据 | 本次观察 | 不代表什么 |
| --- | --- | --- |
| 原生工具链路 | 9 个场景，含真实两步依赖、恶意 worker、路由歧义、执行器 reopen、ACK 丢失 | 不是线上第三方 provider、浏览器或硬件认证验收 |
| 原生最终释放 | 7 个场景，含成功、turn 绑定和不确定结果恢复 | 当前只覆盖内核持有原始值、不超过 32 KiB；不是任意 Agent 合成答案 |
| 有界记账模型 | 1,440 条轨迹；984 次接纳、1,896 次拒绝、6 种记账观测 | 不是全部分布式交错或整个 Rust 实现的证明 |
| 独立轨迹规格与有限状态检查 | S1–S7；11 组状态图全部穷尽，按场景合计 11,788 个状态、59,003 条边；11 个故意削弱版本均有反例；14 项自检通过 | 不是一张覆盖所有特性的联合状态图，不是 Rust 的机械化精化证明，更不是攻击成功率 |
| Rust 回归 | 默认 workspace 通过；特性覆盖通过，具体组合与重跑见记录 | 不将先前失败隐藏，也不声称单次无过滤特性全量通过 |
| 客户端回归 | Python 61 个通过；TypeScript 65 个、9 个文件通过 | 不证明实际安装的 OpenClaw 主机已接好新 broker |
| 冻结清单 | 220 条路径，新增控制/任务/执行边界文件纳入；清单校验通过 | 哈希不是安全认证，也不证明清单穷尽 TCB |

测试经过实际修复：终态先到的恢复、跨层编码/摘要不一致、多结果身份冲突、
路由绑定和 ACK 丢回复。测试记录保留了遇到的失败、重跑原因和平台排除项。
本轮没有测量攻击成功率、任务成功率、延迟、吞吐量、审批时间或用户负担。

## 4. 必须保留的边界

- TCB 分布在认证入口、审批、策略/数据所有者、配置发布、执行器与平台，不只是一个 Rust crate。
- 合同若被用户批准得过宽，系统内的合法动作也可能不符合用户真实意图；需要单独测量合同保真度。
- 内核约束受监控的实际应用请求，不能证明 provider 内部没有额外行为。
- 测试使用受控 worker/provider 和测试信任锚，不能证明本机 Touch ID、浏览器、安装签名或硬件防回滚已可用。
- 执行器日志 reopen 有验证；完整 kerneld 重启后的所有会话/执行句柄重建尚未实现。
  持久化权限与消耗仍保留，但不能称为端到端 exactly-once 或任意崩溃点自动恢复。
- 从未送达的清理 ACK 可能留下保留工件，目前没有自动清理重试队列。
- 通用工具语义、任意最终生成内容及现场 OpenClaw 产品联调不在本增量完成范围内。

## 5. 论文怎么改、下一阶段怎么做

当前英文稿以任务轨迹授权为主线：问题与威胁模型、联合合同、
控制 endorsement、持久化状态、实际请求/响应边界、条件性安全论证、
工程证据、明确未运行的实验方案、相关工作和限制。
不继承 IFC 文献的证明，不以代码行数作为安全贡献，不使用虚构性能表格。

新增规格不再把“内核放行了”当成“安全”的定义，而是独立记录：
用户认证的任务根、预留历史、真实请求/响应、量与尝试次数、前驱成功和 ACK 顺序。
研究重点进一步收紧为这些事实如何跨多个 owner 保持一致。
对比明确承认 IGAC、FORGE、Progent 等已有的任务授权和历史策略能力；
本轮反例只针对我们构造的削弱版本，不能当作对这些已发表系统的漏洞证明。

两个重要边界已写入论文：撤销阻止新预留，不保证撤回已提交操作；
执行器不会独立证明 ACK 中的 commit digest 已落盘，正确顺序仍由可信内核承担。

下一阶段研究重点是：

1. 在已有独立规格、有限图和人工源码映射之上，建立从真实 Rust 状态到规格的
   可检查对应关系，补充更完整的跨任务、时间、部署及存储故障交错。
2. 独立标注用户允许的动作集合，测合同过度授权/欠授权及审批成本。
3. 在相同任务、工具能力和预算下做端到端比较与消融，区分发表系统的原配置
   和我们为机制比较构造的版本。
4. 报告安全、正常任务效用及成本的完整分母和不确定性；收集真实实验后再形成强结论。

是否达到四分或五分，仍取决于新颖性、论证和这些实证，而不是本次提交本身。
