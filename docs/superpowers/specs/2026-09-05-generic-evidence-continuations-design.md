# Savana 通用证据驱动授权与私密任务延续设计

日期：2026-09-05

状态：设计提案 v0.1，待审阅；本文件不表示已实现或已批准部署。

设计代号：EGC1（仅用于区分新增机制，不是已经分配的协议版本号）。

目标：把现有订单场景原型转为可接入生产安全边界的通用机制。

本轮只新增设计文档，不修改运行代码、协议、冻结清单、部署或论文结果。
现有工作树中的 savana-private-workflow 原型及其测试属于上一轮工作。
实现参照为生产基准 73e0684、研究提交 debd3d8，以及当前未提交的场景原型。

## 1. 核心决定

内核处理授权关系、可信事实验证、动作派生、隐私披露和持久化消费；
具体业务的数据格式、资源身份解释和请求协议由经过审查的 Rust 适配器处理。
Python、OpenClaw 和模型负责提出请求、组织流程，不拥有事实签发密钥或执行凭据。

关键区分：

- 通用不等于接受任意 JSON、运行任意规则脚本或相信模型给出的“允许”。
- MCP 已注册不等于它能证明任意事实，更不等于它成为获准接收私密数据的目标。
- 合法事实可以证明一个新资源满足原规则，不能修改原规则。
- 获准操作资源不等于获准向规划模型披露资源内容。
- 派生动作匹配成功不等于已经取得执行凭据。
- 普通数据的完整性标签不会因被用于授权推导而自动升级。

首版保留原有静态合同路径，新增独立、带版本标识的事实派生路径。
两条路径最终使用同一个生产记账所有者和执行安全边界，不建立第二套生产账本。

## 3. 目标、首版范围与非目标

### 3.1 首版目标

1. 用户先认证一组有限规则，具体资源可以稍后才出现。
2. 核心规则执行器不含文件、邮件、订单或商家的专用判断分支。
3. 相同内核二进制可运行文件和邮件两类适配器；差异在注册配置、schema、
   规则和外部适配器。
4. 派生动作依然经过完整动作匹配、G1–G7、必要审批及实际请求校验。
5. 预算、一次性消费、证据版本和公开视图额度跨重启保持。
6. 模型只通过受控观察和动作提议参与多步 loop，不能自行签发事实或声明完成。

### 3.2 首版明确不支持

- 自然语言自动转换成可信授权；模型草案仍需认证确认。
- 任意 Python、JavaScript、WASM 或模型回调作为内核规则。
- 任意正文语义判断直接产生权限。
- 对不完整查询结果做“全部、唯一、不存在、最大、最便宜”等完整性推断。
- 任意私密字段查询、任意生成文本自动降密或任意工具无适配接入。
- 自动规则扩权、热更 schema/事实签发权限、模型自行安装新能力。
- 远端服务内部 exactly-once、完整时序/流量侧信道隐藏。
- 把现有有限状态模型或原型的 26 项测试宣称为新机制的证明。

首版动态规则安装后不支持语义 amendment；撤销或新建认证任务是显式操作。
保留原有静态合同 amendment 的既有语义，不将其默认为动态规则热更新。
新建任务必须重新认证；“每任务一次”不等于“跨所有任务永久一次”。

## 4. 组件与信任边界

| 组件 | 负责 | 不得负责 |
| --- | --- | --- |
| 认证入口 / 任务签发 / approvald | 获取用户确认的规则、参数、披露对象和上限；准确展示 | 把模型草案或动作审批直接当成任务授权 |
| policy-core 内通用验证器 | 有界规则检查、事实验证、完整动作派生、证据重验 | 网络 I/O、任意业务代码、自然语言裁决 |
| kerneld 数据与持久化所有者 | 私密数据句柄、证据引用、当前状态、预算、披露记录、dispatch 事务 | 把未提交结果或未经释放的数据交给 Python/模型 |
| 隔离的 Rust 适配器 | 数据源协议、受审查的语义映射、稳定资源标识、业务请求构造 | 修改用户规则、选择自身信任根、绕过内核放行 |
| execd 及可信 transport | 检查实际请求/目标/凭据，执行 fence，保留实际响应 | 相信 worker 自报成功或用另一个请求替换获批请求 |
| agentd / OpenClaw / Python | 提议查询和动作、接收允许公开的进度 | 持有内核值存储、原始证据接口、签发密钥或自主调用生产 provider |

“适配器在内核外”不代表它不影响安全。事实的业务含义和执行前置条件属于
明确的 TCB。要审查、限定权限、绑定版本并隔离部署，不能把普通 MCP worker
签个名就提升为可信适配器。

事实来源允许两种经过登记的模式：

- 原生签名源：内核验证来自已授权来源的签名、声明范围与绑定关系。
- 经验证的连接器结果：可信 supervisor 验证实际连接/请求/响应，受审查的 Rust
  解码器从保留响应产生结构化声明。未签名 provider 的普通 JSON 不直接变成证据。

第二种模式中，不能由被视为不可信的 worker 解码任意内容，再让 supervisor
不经检查盲签。可信映射实现及其实际输入必须受约束。

## 5. 数据模型

以下名字是拟新增的逻辑类型，不是当前已存在的 Rust API 或已分配的 wire tags。

### 5.1 TaskPolicy

包含：

- 格式版本、installation、principal、durable_task、policy_id、revision。
- 当前部署代数、manifest、schema/事实权限/profile 注册表身份。
- 起止时间、规则集合、资源范围常量和获准的查询模板。
- 工具/effect/目标约束、动作参数来源规则、步骤依赖。
- 任务级及规则级次数/量预算、每资源限制、发现上限。
- ActionApprovalPolicy：哪些动作需要逐次审批；用户规则不能降低部署强制审批下限。
- DisclosurePolicy：接收模型身份、允许的投影 schema、额度及有效期。

TaskPolicy 的确认绑定准确结构化内容和版本，不只确认一句宽泛的任务名称。
工具变化、接收者变化或额外能力不能作为普通参数更新悄悄进入旧授权。
首版动态分支默认保持外部 MCP 调用的逐次审批要求，发现调用也不自动豁免。
任务级规则批准不能取消既有动作审批；任何未来免逐次审批策略须另行显式批准。

### 5.2 SchemaDescriptor 与 FactAuthorityGrant

SchemaDescriptor 描述稳定字段 ID、类型、单位、命名空间、规范化方式、字段角色
及语义映射版本。首版字段类型是有限的布尔、整数、枚举、时间、资源引用、
主体/目标引用和有界标识符，不提供任意对象或脚本类型。

字段角色至少区分：

- AuthoritativeMetadata：允许特定来源就特定范围作出的结构化声明。
- UntrustedContent：正文/备注或由不可信内容推断的结果，不可直接作为授权依据。
- OpaqueValueReference：引用内核私密数据；引用本身不授予读取权限。

FactAuthorityGrant 指定哪把密钥或哪个受验证映射实现，可以证明哪些 schema、
字段、命名空间和资源范围，并绑定时间/代数/撤销状态。
不能只按“连接器整体可信”授予全部字段证明权。
其发布权限来自签名部署配置；首版不复用用户添加 MCP 的自助注册权限。

### 5.3 ResourceIdentity 与 ResourceVersion

ResourceIdentity 由来源身份、命名空间及规范化的稳定对象身份组成，
不是模型生成的字符串，也不把当前文件路径、邮件主题当唯一身份。
ResourceVersion 单独记录内容或元数据版本。

消费计数使用稳定资源身份，不使用版本、展示路径、handle、查询 nonce 或 plan ID。
同一资源改名、换别名、更新版本、换查询不能重置已消费次数。
文件的硬链接/路径别名、邮件的稳定 ID 由适配器契约定义并测试；来源乱造新身份
是信任假设失效，内核无法凭签名发现这种语义撒谎。任务总预算仍提供额外上限。

### 5.4 EvidenceRecord

绑定 policy/task、获准查询及其真实 execution 身份、query nonce、源与映射身份、
schema、资源/版本、结构化声明、观察时间、失效时间、源快照版本和来源证明。

原始正文留在现有私密数据存储，不放进授权字段表。需要保留原始结果时，仅以
私有引用和来源证明关联；引用摘要、事实摘要也不得直接作为模型可见句柄。

证据可有“证明已返回对象属于查询结果”的成员语义，但不默认具有全集语义。
EGC1 不开放 CompleteDomainEvidence；完整快照证明留待单独版本设计。

### 5.5 VerifiedDerivedAction

内核生成、字段私有、不可由普通反序列化或调用者布尔值构造。
绑定完整的工具/profile、effect、资源/版本、目标、参数/载荷引用、量与单位，
以及 policy/rule、事实见证、schema/profile 版本、前置状态和有效期限。

它是匹配证明，不是 dispatch grant，不含可绕过审批独立使用的 provider 凭据。
缓存候选展示可以使用独立 handle；执行前必须以当前状态重新建立或重验该证明。

### 5.6 DisclosureSchema 与 PublicView

DisclosureSchema 是经审查且在部署许可内的封闭投影定义，不是外部回调。
PublicView 仅含该接收者获准看到的类型、任务内不透明标识、关系及粗状态。
不存在“任意选字段”“任意 yes/no 问题”或直接返回私密摘要的默认接口。

## 6. 有界规则语言

首版采用确定性、非递归的结构化 AST，不引入通用脚本引擎。
一条规则按有限合取表达，OR 用多条有独立 ID 的规则表达。

允许的基本条件：

- 已验证元数据与认证常量的类型化相等、有限集合成员和数值/时间区间。
- 多条证据之间类型兼容的字段相等连接。
- 资源所属范围关系；必须来自已验证的结构化归属证明，不能靠路径字符串前缀。
- 绑定到确切前驱动作身份、资源关系和 completion epoch 的已验证成功条件。

规则依赖必须无环；具体实例的前驱绑定由内核检查，不能以“某个别的动作成功”
替代要求的前驱。动态发现不能为已预留动作改写依赖关系。

参数表达式首版只有认证常量、符合字段角色的证据字段、受约束私密值引用，
以及由已登记 profile 定义的有限构造。没有任意字符串拼接、URL 模板执行、
正文正则查询、算术程序或模型回调。

检查顺序为类型和字段权限检查、有限匹配、完整动作构造、目标及参数约束。
不先把各字段分别放入白名单再任意拼接。

若不同规则生成语义相同的动作，应去重并共享任务/资源消费约束；
不能通过另一个 rule_id 绕过每资源一次。规则级预算是额外约束，不替代总预算。

建议首版硬上限如下；是工程初值，不是已测性能结果：

| 项目 | 建议上限 |
| --- | --- |
| 每任务规则 | 16 |
| 每规则事实变量 / 谓词 | 4 / 32 |
| 单次事实 batch | 256 条、规范编码不超过 256 KiB |
| 每任务有效事实 / 派生实例 | 1,024 / 256 |
| 每任务查询尝试 / 不同公开视图修订 | 32 / 256 |
| 每次推导匹配工作量 | 10,000 个计数步骤 |

根规则只能收紧部署上限。还需全局内存/持久化字节、任务数、响应字节和查询速率
上限；实现前与现有部署硬限制统一，不按“任务数乘最大值”无限分配。
派生实例上限计入该任务历史上已产生的实例和墓碑，不仅计算当前可见候选；
回收显示记录不能腾出新的执行机会。事实回收也不能删除仍被证明/计数依赖的索引。
连接组合、扫描、输出候选均计入确定性工作量预算，耗尽时整次推导不发布部分
结果，不把达到上限解释为已经搜索完整。算法不依赖 wall-clock 超时充当唯一边界。

## 7. 查询、事实接纳与动态实例

### 7.1 发现本身必须先获得授权

发现不是一条可以先读取所有私密数据再筛选的后门。
TaskPolicy 中的 QueryTemplate 已绑定数据源、资源范围、参数来源、目标和预算。
调用查询同样通过现有访问、出站、审批和执行检查；只读请求也可能向外泄露查询词。

查询句柄由内核发放。分页 cursor 由内核私有保存并绑定获准查询；
模型不能自填 URL、目录、邮箱账号或原始 cursor。每次真实查询尝试计费；
换页、换 plan、重试和新 nonce 不重置查询预算。

### 7.2 接纳事务

1. 从确切的、已获准的执行结果中验证来源证据及请求/响应关联。
2. 检查角色授权、schema/映射版本、任务和查询绑定、时间、新鲜性及撤销。
3. 验证资源身份、重复记录、规范编码和有界大小。
4. 检查同一来源/命名空间/查询范围/快照种类的版本不倒退；
   同版本的授权元数据不得相互冲突。
5. 在私有候选状态中执行有界匹配、去重并更新依赖关系。
6. 原子提交事实引用、版本状态、候选状态和获准视图记录，再对外可见。

整批失败不产生部分权限。重复的同一接纳结果是幂等观察，不新增候选和额度。
事实拒绝细节只进入受保护审计，不把私密值、摘要或细粒度错误交给模型。

快照一致性只比较已声明为授权相关的元数据，不把正文、备注及未授权字段的
摘要变化变成可观察的接受/拒绝旁路。

### 7.3 更新与有效期

每次新提议/prepare 都重验相关事实和当前 policy/schema/registry 身份。
有效期取根规则、事实、签发权限、审批和执行 lease 允许窗口的交集。

资源版本变化使旧候选失效。未预留的新版本可在原规则内重新派生，
但继承稳定资源身份的消费记录。已经 Reserved 的动作不被静默替换，
执行时旧版本前置条件不成立则停止；不得换成新版本继续原动作。

事实过期或撤销不删除消费墓碑。GC 只回收不再需要的内容，不能遗忘稳定身份、
计数、已预留绑定及必要审计。达到容量上限时拒绝新工作，不通过删除计数腾空间。

### 7.4 “发现完了”与“做完了”分离

当前没候选、达到查询上限、处理完已知对象，都不等于处理完所有符合条件的对象。
首版只报告已知实例的动作进度；没有完备性证据就不返回 VerifiedTaskComplete。
“发现更多”可以继续 loop，但不能让模型凭一句“应该都找完了”解锁依赖全集的动作。

## 8. 通用匹配如何接入现有内核

内核内部拟引入带封闭分支的 VerifiedActionAuthority：

- StaticContract：保留现有 VerifiedTaskMatchV2 和完整合同域语义。
- EvidenceDerived：使用新规则、见证和 VerifiedDerivedAction。

这不是给旧 public 类型添加一个可任意填写的来源字段。
两个分支有独立 wire schema/hash domain/验证入口，统一暴露经过验证的完整动作
和消费投影供后续安全边界使用。未知分支在所有旧服务上 fail closed。

动态分支形成与既有七个控制面相同的约束覆盖：
Tool、EffectKind、Scope、Magnitude、Argument、Destination、Trigger。
这些不是新增的 G1–G7。动态 witness 必须绑定整个动作，不接受七份能自由混搭的证明。

内容承诺仍先于审批。审批展示精确动作及来源规则/版本；动态动作变化必须重新审批。
后续授权承诺绑定已验证证据、确切审批、状态转移和执行内容，避免循环摘要依赖。
新证据类型不能作为普通 KernelValue 或 ProvenanceRecord 父节点来提升数据完整性。

生产接入至少覆盖：

- 当前 manifest、connector 注册表、tool/profile 和调用者身份检查。
- 现有数据标签、溯源、参数验证与出站接收者约束。
- 按部署和任务要求的动作审批。
- 唯一 durable owner 内的原子消费与 dispatch 绑定。
- execd 对实际请求、目标、凭据和 profile 前置条件的验证。
- 实际结果的保留、认证分类、vault 入账与完成状态提交。

不允许把研究原型的 ProviderTransport hook 接到产品中代替这条路径。

## 9. 持久化、恢复和执行语义

### 9.1 唯一生产事务所有者

扩展现有 durable snapshot，而不是把原型 FileStore 搬成独立生产库。
新规则、稳定资源计数、证据索引、候选、审批消费、公开视图记录与 dispatch
引用由现有 owner 管理；私密大对象仍由 vault 管理。

跨 owner 的大对象保留不是假定存在一个分布式数据库事务：
先持久化不可变 vault/execd 记录，验证其存在与绑定，再提交引用和任务状态。
提交前失败最多留下可回收的孤儿，不可出现指向未持久化材料的已公开授权。
GC 必须遵循引用/ACK 顺序，保留现有不确定恢复语义并增加对应崩溃测试。

### 9.2 状态与消费

逻辑状态为 Candidate、PendingApproval、Reserved、Attempted、Retained、
Succeeded、Unknown；过期/撤销/前置条件失败可使未执行候选变为 Unavailable。
这些是新分支的语义模型，最终 wire tag 不在本提案中分配。

- Candidate/PendingApproval 不消费业务动作次数；产生它们的真实发现请求已消费查询额度。
- 原子 prepare 同时重验 policy、证据、状态、依赖、审批和额度，并持久化 Reserved。
- 任务/资源尝试计数从 Reserved 起永久消费；首版动态分支无自动重试、无返额。
- Execd 持久化 Attempted 后才允许一次受监控 transport attempt。
- 先保留真实响应，再分类、提交结果及完成状态；最后才对模型公开进展或 ACK 清理。
- 没有可认证完成依据的尝试保持 Unknown；模型自报完成不能推进依赖。

旧静态分支已有的、合同允许且经过验证的 NoEffect 返量语义保持不变。
不能因新分支采用保守策略而顺便改动旧合同含义。

### 9.3 撤销与 TOCTOU

首版采用与现有静态路径一致的 prepare 线性化边界：
撤销提交后禁止新的预留；已持久化 Reserved 的操作不承诺立即撤回，
可在原 lease 和执行前置条件仍有效时继续。UI 必须区分“停止新动作”和
“远端已经开始/可能继续的动作”。不宣称即时全局取消。

资源状态可能在发现后变化，不能只靠事实 TTL 解决 TOCTOU。
执行 profile 必须规定如何在实际操作时验证资源版本/范围：
本地文件使用稳定对象身份及受限句柄/安全解析，远端采用可验证的条件更新等。
做不到时，该 profile 不得宣称版本绑定语义得到保证；首版受影响动作不启用。
这仍不证明 provider 内部没有额外副作用。

### 9.4 恢复

- prepare 回应丢失：按原请求身份恢复同一预留，不新建 nonce 重扣或重发。
- Reserved 尚无尝试 fence：允许恢复同一预留，重新检查原执行前置条件。
- Attempted 无保留响应：Unknown，不重发。
- Retained：从已认证保留响应继续分类，不调用 provider 第二次。
- 终态：幂等返回已有结果；不再次消费、返还或解锁依赖。
- 存储提交不确定：停止当前 owner 的新操作，认证重开后对账。
- 状态恢复不自动新建任务、换根规则或清空披露/资源计数。

上述是新路径必须实现和测试的恢复契约，不是声称目前已具备完整 kerneld
会话/句柄恢复。若产品恢复所需句柄无法重建，不以“恢复安全但不可继续”冒充可用性验收。

## 10. 私密闭环与允许泄漏

### 10.1 公开面

模型只能获得与其精确身份、任务和投影 schema 绑定的 PublicView。
默认字段限于：schema/视图修订、任务内不透明模板/资源/动作句柄、允许公开的
工具类别及关系、可发现状态和粗动作状态。

句柄使用随机任务密钥及内部序号生成，不使用私密值的内容哈希。
原始资源 ID、地址、查询参数、事实/请求摘要、细粒度错误、源正文不默认出现在公开面。
句柄按任务和调用者角色隔离，复制到别的任务不能使用。

类型和状态本身也可能透露信息，必须是用户确认且部署规则允许的披露，
不能因为它们不是明文就免走释放门。

### 10.2 释放与计费

动态投影通过现有 PlannerCall / 适用的解密级入口，绑定签名规则、
实现身份、接收者、任务和实际输出字节；任务规则只能收紧部署释放权限。

每个接收者/schema/语义视图修订的首次释放先记账再发送；丢回复不返额。
无语义变化的内部 fence/响应保留不单独增加公开 epoch。
仍有效且仍是当前视图的缓存可重复发送，不产生新的披露修订。

如果下一次公开状态变化会超额：私有事实和终态仍正常提交，
该公开通道停止发布新视图并返回统一 Unavailable；不继续发送误导性的旧 Ready 状态。
缓存重读仍检查会话、撤销、有效期和当前释放权限，缓存不是永久阅读许可。

Malformed、未知命令、过期句柄、越权提议统一返回受限拒绝；
详细审计由认证用户或可信运维接口读取，不传给规划模型。
用户需要的审批展示通过独立可信 UI，不把审批内容或凭据塞进 planner 回复。

### 10.3 可检查的隐私目标

单独定义允许泄漏函数 L，而不是把实现实际输出的所有东西事后称为允许泄漏。
首版 L 可以包含已批准的程序/工具类别、槽位数量与跨轮次相等关系、
授权相关条件/新鲜性/版本一致性事件带来的公开进展、粗结果和额度耗尽。

对相同认证规则的结构、相同允许泄漏事件、同一自适应命令序列的两组有效运行，
在一致重命名资源并耦合随机句柄密钥后，要求序列化 planner transcript 相同。
禁止泄漏的值发生变化时，不得通过内容哈希、错误细分或隐式 epoch 变化区分两组运行。

这是待实现、待验证的关系式目标，不是已经拥有的不干扰定理。
不覆盖时序、调度、包长、provider 观察、获准接收者后续滥用，
也不证明任意不同用户意图之间等价。固定拒绝和配额单独都不能建立该保证。

## 11. 接口设计与调用权限

下面是逻辑操作，不是承诺新增相同数量的公网 HTTP/RPC 路由。
实现时复用现有认证会话和编解码框架，新增 schema/分支必须显式协商。

### 11.1 模型侧：三个受限操作

| 操作 | 可提供输入 | 返回 |
| --- | --- | --- |
| observe | task_handle | 当前获准 PublicView 或统一 Unavailable |
| discover | task_handle、query_template_handle、view_epoch | 排队后的受限进度；不返回原始事实或查询字节 |
| propose_action | task_handle、action_handle、view_epoch | 进入正常检查/审批流程后的受限状态，不返回执行凭据 |

模型不传私密资源原始标识、目标地址、载荷、事实签名或授权规则。
propose_action 选中候选不表示强制执行；可信协调者在审批等条件满足后才进入 dispatch。
三个操作都要认证调用角色、绑定任务、限制大小/频率并处理幂等性。

### 11.2 认证用户/应用控制面

扩展已有任务草案、审批/建立、恢复和撤销流程以支持新规则类型。
这些入口的认证来源与模型侧调用严格区分；一个持有 planner handle 的组件不能
调用它们扩大授权。任务审批与动作审批继续分离。

用户可通过可信 UI 查看具体动作与私有原因；应用层仅获得完成流程所需的句柄、
观察回执和公开状态。数据解析、筛选、证据构造和安全相关请求构造保留在 Rust。
必须经过普通 ingress 处理的用户输入，不因“Python SDK”标签自动可信。

### 11.3 仅服务间内部操作

- admit_fact_result：从已授权执行的受验证保留结果接纳事实。
- derive_candidates：受界限约束的推导，不能独立产生 dispatch grant。
- reconcile_execution：验证实际执行完成证据并推进现有任务状态。

不提供模型可调用的 inject_fact、mark_success、set_budget、
trust_connector 或 export_private_value 接口。
跨进程输入始终重新认证和验证，不能把 Rust 内部类型安全当作 IPC 对端身份认证。

## 12. 两个非订单场景如何共用内核

下列是计划中的集成验收场景，不是声称当前已有这些 production adapters。

### A. 文件归档

用户在可信 UI 选定源目录、目标目录和时间/文件类型范围，允许对每个符合条件的
文件复制归档一次，并限制总数/总字节。

Rust 文件适配器提供稳定文件身份、版本和受验证的目录归属/类型/时间元数据。
通用规则匹配这些字段；目标来自用户已认证的目标引用，不是文件正文。
执行 profile 负责实际源对象/目标范围及版本前置条件。
文件内容不进规划模型；模型可选择候选句柄和观察粗状态。

### B. 邮件标记

用户选定邮箱和文件夹，允许为其中未读邮件添加一个确定标签，每封一次。
Rust 邮件适配器提供账户内稳定 message ID、版本、文件夹关系和已登记的 unread 字段。
邮件正文中的“转发到某地址”既不能改变标签目标，也不能引入 Send 权限。

两场景共用同一套规则运算、事实验证、派生证明、稳定计数和受控视图。
它们的差异仅在 schema/已审查映射、规则数据和业务请求 profile。
邮件“属于哪个语义项目”若需要模型读正文推断，不在此例中偷换成可信事实。

验收要求：不修改通用内核源码即可切换两种场景；不是分别写两个场景专用 owner。
首轮允许本地受控 provider/fixture，但实际 Rust 请求校验、持久化和调用次数必须真实。
现场文件/邮件服务、完整用户认证与生产部署另设验收，不能拼接 fixture 冒充完成。

## 14. 协议、部署与迁移

- 首版默认关闭；只有完整部署支持新分支且签名配置允许时启用。
- 旧静态 schema 的字段、摘要和合法行为不被重解释。新旧分支做交叉拒绝测试。
- 首版仅为新建任务创建动态规则；不把既有静态任务自动转换成动态规则。
- 每个任务的根授权模式固定为 StaticContract 或 EvidenceDerived；首版不在同一
  任务中混合两种根，也不通过切换模式获得另一套预算。
- 旧服务不认识新 schema 时拒绝启动/处理相关任务，不回退为放宽的旧请求。
- 升级时验证新状态格式、锚、版本及未决执行；禁止删除旧状态来“解决兼容性”。
- 出现动态状态后，不允许旧二进制把未知部分忽略后继续写回；降级需显式安全路径。
- 保留生产 release 的原冻结基线。实现通过后审查新文件覆盖和协议向量，
  再建立新版本冻结清单，而不是为了让检查通过提前重算哈希。
- 设计和开发不自动授权安装、证书修改、Touch ID 清理、生产数据迁移或 push。

## 15. 安全义务与验证门槛

拟新增独立规格，至少覆盖以下义务：

| 编号 | 义务 |
| --- | --- |
| E1 | 所有动态权限均可追溯到认证规则；普通值、模型输出、工具注册不能成为授权根 |
| E2 | 每个实际预留动作都匹配同一完整关系，证据来源/字段/范围/版本符合规则 |
| E3 | 同资源的别名、版本变化、重发现、重规划、恢复不能补充消费额度 |
| E4 | 新预留以唯一 owner 的当前状态原子检查并消费；并发竞争不能多放行 |
| E5 | 实际请求、目标、凭据和资源版本满足原授权绑定，不由 worker 替换 |
| E6 | 只有保留并验证的实际完成证据可解锁确切后继；Unknown 不等于成功 |
| E7 | 公开字节必须通过获准投影与现有释放门；禁止字段不能通过摘要/拒绝/epoch 泄漏 |
| E8 | 崩溃、存储不确定、状态回滚和协议混版不造成重复执行或权限复活 |
| E9 | 部分发现不能用于全集、唯一性、否定或任务全完成结论 |
| E10 | 动态 proof、控制 endorsement 与普通数据溯源类型保持不可混用 |

实现验收分为四组：

1. 机制与协议：类型/角色/上下文/时间/版本/规范编码、字段权限、源签名、跨任务
   重放、候选拼接、循环依赖、整数/资源上限、混版拒绝、旧静态回归。
2. 持久化与执行：在事实保留/接纳、审批、prepare、attempt、响应保留、终态、
   公开视图、ACK 前后注入故障；包括并发一胜者、别名去重、版本 ABA、锚回滚、
   过期和撤销竞态、精确请求替换、依赖绑定和恢复后重复调用计数。
3. 隐私：基于独立 L 的自适应双世界测试；改变禁止披露字段、查询拒绝、重复观察、
   实际结果与公开状态、额度用尽、崩溃重开；同时验证允许的计数/状态差异可见，
   防止用“全部拒绝”伪装成功。
4. 集成与通用性：文件与邮件场景使用相同核心二进制和 ledger；经过真实生产协议
   边界与受控 Rust adapter，不可绕过审批/释放/execd。随后单独验收现场认证、
   网络/OS 隔离和实际业务服务。

独立有限状态模型、源码对应和测试不能相互冒充。
模型扩大后必须重新记录边界、状态/边数、反例和未覆盖交错。
论文的原创性、攻击/效用/审批负担比较与性能结果仍需真实实验，不由本设计保证。

## 16. 实施顺序与停止条件

### P0：冻结设计与编码契约

确定 schema/字段授权、规则 AST、稳定身份、公开 L、摘要输入与状态迁移。
产出接口规格、黄金向量、独立安全义务及失败行为；本提案不分配最终 wire tags。

### P1：实现纯通用验证机制

在 protocol/policy-core 完成规则与事实验证、完整动作派生、负向测试。
此阶段没有可绕过生产边界的 dispatch；用文件/邮件 facts 验证无业务硬编码。

### P2：接入既有持久化所有者

实现动态状态、稳定计数、版本/墓碑、并发原子性、公开视图记账和恢复。
完成崩溃切点与回滚验收后才进入执行接线。

### P3：接入审批、释放和执行器

增加新分支真实协议链路、既有 G1–G7/注册表/manifest 检查、
实际请求/响应绑定、结果保留和精确接收者视图释放。
不把孤立模块测试完成称为“内核已经支持”。

### P4：SDK / Agent loop 与双场景集成

让三个模型操作通过认证协议工作；完成文件、邮件共用同一内核的集成测试，
包括重复发现、真实请求篡改、恢复继续、拒绝/审批/额度耗尽和隐私对照。

### P5：版本化交付与论文对齐

运行新旧回归、冻结范围审查、迁移/恢复/混版检查并记录实际结果。
只有真实完成的能力进入论文实现章节；未运行实验继续标为未运行。
生产部署、真实账号测试和外部推送按单独授权执行。

阶段停止条件：如果一个业务需要新增任意代码解释器、无法保证稳定身份、
无法证明允许使用的字段来源、无法在实际执行时落实必要前置条件，
或必须放宽既有安全门才能通过，则将该业务标为不支持并回到设计审查。
不默认授权扩展 TCB 或缩小安全承诺。

## 17. 本提案的边界结论

这个方案的目标不是让内核理解“订单”“邮件正文”或用户自然语言，
而是让它验证：谁认证了什么规则、哪些来源能证明哪些关系、当前完整动作是否
符合这些关系、还能执行多少次、模型能看到什么，以及真实执行是否与授权一致。

代价是 schema/profile 与可信适配器需要审查，首版表达能力有限。
收益是否足以构成高接受论文，仍要通过通用性、形式论证和公平实验评价。

本轮交付仅为该设计提案。此前有界原型的状态和验证见
[原型规格](../../research/private-continuations.md)及
[原型验证记录](../../verification/private-continuations.md)。
