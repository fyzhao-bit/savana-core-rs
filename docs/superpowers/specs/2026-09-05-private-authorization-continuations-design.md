# Savana 私密授权状态与可恢复续行设计

日期：2026-09-05

状态：设计提案 v0.1；未实现，未证明原创性，未批准生产部署。

本文只新增设计文档，不修改运行代码、旧设计、论文、冻结清单、部署或用户状态。
现有未提交改动保持原状。文中的新增类型和 API 均为逻辑设计，不是现有接口承诺。

## 1. 核心问题与决定

授权反馈也可能泄露隐私。模型先使用查询 A 的结果，再使用查询 B 的结果，若
收到“已消费”，就可能知道两个私密查询命中了同一资源；若换版本/handle 后
重新给一次机会，则虽然隐藏了关联，却破坏了消费限制。

候选研究主张是：将私密事实、权限判断、稳定消费历史和模型可观察反馈纳入同一
可恢复的续行语义，在原始授权不扩大的前提下，让有限的合法动态任务继续执行。
“IFC + capability + 持久化”本身不是本文声称的新发现。

四个生命周期必须分离：

| 对象 | 可变化内容 | 不得随变化发生的事 |
| --- | --- | --- |
| 根授权 | 首版任务内仅撤销，不热改语义 | 工具、范围、目标、预算、披露规则自动扩张 |
| 私密证据 | 新资源、事实版本、有效期、撤销状态 | 来源内容自行变成新的授权规则 |
| 派生候选/续行状态 | 缓存失效、重新匹配、私密分支推进 | 新候选被视为新额度 |
| 消费与披露账本 | 单调累计，终态结算与墓碑 | 更新、恢复、GC、换会话使历史消失 |

授权范围不扩张，指每个新动作实例都满足原始认证规则，不指候选集合永不增长。
本方案保护对云端规划器的披露；不声称秘密永远不离开任何组件，获准目标及本地
用户界面可以按各自权限接收信息。

## 2. 与旧提案的关系

基础设计见 [通用证据驱动提案](2026-09-05-generic-evidence-continuations-design.md)。
新设计继承它的字段级事实权限、独立动态证明分支、同一生产 owner、G1–G7、
逐次审批、精确执行请求、固定任务模式和默认关闭的迁移原则。

对新建的私密续行模式，下列条款覆盖旧提案的对应默认值；旧文件保留作历史记录：

1. 不默认公开资源槽位、资格、can_discover、余额、Unknown、版本失效或去重结果。
2. 不因私密预算不足直接向模型返回 Unavailable；统一错误码也不能隐藏“是否错误”。
3. 不以“输出字节是否变化”计算新披露。对新快照重新求值，即使结果相同，仍是新观察。
4. 不默认以实际完成时间推进公开 epoch 或关闭模型会话。
5. 私密模式不提供逐资源候选选择接口，模型选择的是预先批准的程序入口。
6. 执行与披露是两条有因果关联的持久化流程；披露又分固定输入和冻结输出两个事务，
   不假定远端执行和信息送达可原子化。
7. 恢复 Reserved 不仅检查本地没有 fence，还需认证执行器日志能证明原动作未尝试。
8. 允许泄漏规格不再笼统包含所有授权、新鲜性和协议进展；必须逐项列出。

## 3. 威胁模型与边界

不可信：云端模型、OpenClaw/Python 规划层、模型可见工具返回中的攻击内容、
恶意重复/并发请求以及它们控制的会话重连与重新规划。

可信：认证用户入口、经审查的规则检查器和本地续行器、现有私密值存储、
持久化 owner、执行器、来源身份/字段用途登记以及受审查的 Rust 适配器。
事实签名只证明谁声明了哪些字节，不能证明来源从未撒谎。

部署要求完整中介：不可信规划进程没有原始 provider 凭据、私有 IPC 读取权或
直接读取私密日志的权限。不能把新本地续行器作为普通 Python/agentd 回调运行，
再假设同进程的“私有变量”构成隔离。私密执行事件不经过模型可见工具通道。

首版目标包括 API 消息、字段、消息类型、集合形状、标识相等关系及逻辑发布轮次。
不包括墙钟延迟、CPU/磁盘竞争、网络流量、原生子进程旁路、获准远端串谋、
宿主管理员读取或任意物理回滚。物理回滚保护依赖独立可信锚。
公开基础设施可用性是关系式论证的环境前提，不能把由秘密决定的正常拒绝伪装成
外生故障。覆盖全时序侧信道需另外设计调度隔离、填充和流量协议。

用户仍需完成当前部署规定的逐次 MCP 审批，发现调用也不自动豁免。审批数量、
详细内容与私密原因走独立认证 UI；云端是否能获知“等待审批”须单独允许。
本轮不减少审批次数，也不声称完成无人值守产品流程。

## 4. 根契约与三个约束面

拟新增 `PrivateContinuationContract`，由认证入口确认其规范化结构，而不是仅确认
任务名称或模型摘要。契约包含：

- 稳定 task/principal/installation lineage、期限、模式和部署绑定。
- 固定的规则、query templates、字段允许用途、来源与执行 profile。
- 允许的本地程序入口、公开参数类型/范围、依赖和步骤上限。
- `ConsumptionSpec`：任务、逻辑消费域、每资源及查询的预算。
- `DisclosureSpec`：精确接收者、可释放函数、精度、观察时机/次数和历史阅读权限。
- `PublicAdmissionSpec`：公开提交配额、速率窗口、提交/观察期限。
- 审批要求、私密结果的用户接收者、故障和撤销语义。

三个约束面相互独立：

| 约束面 | 决定 | 不能替代 |
| --- | --- | --- |
| 动作授权 | 是否可以针对这个资源执行这个完整动作 | 不能因此公开资格或原文 |
| 消费约束 | 当前是否还存在一次合法机会 | 不能因此公开去重或余额 |
| 披露约束 | 这个接收者可以知道什么 | 不能增加动作权限或恢复额度 |

首版根契约不支持语义热修改；改目标、规则或扩大披露需新的显式认证授权。
恢复不得自动建立新 task。跨任务“永远一次”需显式账户级消费域，不从每任务限制推导。

## 5. 私密授权状态的类型规则

所有普通值和授权派生值都具有保密约束、完整性来源与依赖。
保密约束在组合时取共同允许的接收者；完整性沿不可信依赖保守传播。
实现复用现有 label/provenance 体系，不引入互不兼容的第二套标签。

以下操作的结果属于受保护的内核值，而非可以直接序列化的 bool/int：

| 派生值 | 至少依赖 |
| --- | --- |
| Eligible(resource, rule) | 资源身份、资格事实、范围关系、规则 |
| SameResource(a, b) | 私密身份解析和别名关系 |
| Spent(domain, resource) | 稳定资源身份、消费记录及其存在性 |
| Remaining(domain) | 该域所有可能影响余额的消费与控制条件 |
| ContinuationEnabled(node) | 依赖结果、审批、资格、余额和撤销 |
| Outcome(reservation) | 精确请求、被执行资源和实际保留结果 |

第一版保守地将资源/动作账本整体划为 TaskPrivate，不尝试按实际数据内容自动降级。
消费域的标签由所有可能写入者的静态依赖确定，不能因为某次尚未消费就把空账本
标为公开。公开预算上限不意味着剩余预算公开。

规则检查包括：

- 分支的控制标签 `pc := pc join label(condition)`。
- 遍历继承集合成员关系、数量和顺序的标签；异常、上限耗尽、提前返回亦然。
- 赋值、状态更新及任何输出同时受值标签与控制标签约束。
- 不能通过重新包装结果、丢弃父节点、换 handle 或重建缓存洗掉来源。
- 产生外部动作不要求其所有参数可向云端公开；要求根授权允许此私密数据参与
  对应控制/参数用途，且真实接收者通过现有信息流与出站检查。
- 授权用途的 endorsement 与数据完整性提升、向云端 declassification 严格分开。

签名字段不自动具有权限语义。例如服务器签名的邮件 From 仍可能来自攻击者；
`FactAuthorityGrant` 必须绑定 schema、字段、资源范围及 `permitted_authority_use`。
首版不允许任意正文分类、模型推断或不可信布尔值自行授权一个动作。

## 6. 有界本地续行与云端职责

内核执行受限、可检查的 AST，不执行 Python、任意 Rust 插件回调或模型生成脚本。
建议首版节点：

| 节点 | 含义 |
| --- | --- |
| Discover(template, bound_params) | 通过现有授权/审批路径发起受限查询 |
| Select(predicate_id, evidence_refs) | 根据已批准的类型化谓词筛选，不接受任意查询表达式 |
| ForEachBounded(collection, max_items) | 遍历有界已发现成员，不推断全域完整性 |
| If(condition, then, else) | 私密条件只在本地分支 |
| Attempt(rule, domain, resource) | 尝试建立原子预约，再走既有执行边界 |
| Await(reservation) | 根据可信保留结果推进，不接受模型自报成功 |
| OfferObservation(slot, value_ref) | 提交私有披露候选，不能自行向模型发送 |

`Attempt` 的 AlreadyCharged、NoBudget、Ineligible、Stale、NeedsApproval 都是本地
结果。是否公开、公开精度与时间，由另一个发布状态机决定。
AlreadyCharged 不等于此前成功；只有匹配的 Succeeded 才能解锁要求成功的后继。
Unknown 不能换一个计划节点再试。

模型选择已批准的程序入口及有限公开参数。例如选择“执行查询 A 的归档步骤”，
而非提交“对私密字段不断改变阈值”的代码。入口 handle 在任务建立时按公开
程序目录生成，不随私密候选数量变化。
模型可以根据获准反馈选择下一入口；未准披露的决策留在本地，不承诺云端可以
既完全不知道一个秘密区别，又依据它选择不同分支。

首版检查器只做保守可行性判断：一个模型可见输出必须能证明为公开，或有一个
精确匹配的披露槽。否则保留本地或拒绝契约。不是任意程序的最优切分编译器。
后续若研究自动切分，需另行定义语言、正确性和最小披露目标。

## 7. 稳定身份与动态证据

内部拟使用：

```text
TaskKey     = (InstallationLineageId, TaskLineageId)
ResourceKey = (LogicalSourceId, NamespaceId, CanonicalObjectId, Incarnation)
ChargeKey   = (TaskKey, ChargeDomainId, ResourceKey)
```

`Incarnation` 在数据源可能复用对象编号时必须明确；由经过验证的身份契约定义，
不是每次发现随机生成。文件移动/硬链接、邮件移动/复制的“同一对象”含义由
适配器契约给出。恶意来源随意声明新身份仍属信任假设失效。

ChargeKey 不包含当前资源版本、路径、handle、query nonce、plan ID、规则修订、
schema/profile 版本、当前签名公钥或 connector 注册实例。
多个规则共享同一逻辑机会时必须映射同一 ChargeDomainId；规则自身限额只是额外
约束。密钥轮换和 connector 重连需可信映射到同一来源 lineage。
无法证明身份连续性的更新暂停任务，不能自动当作新来源、新资源继续给额度。

`EvidenceCut` 保存所有授权相关事实的版本、来源范围、观察窗口、撤销代数及一致性模式。
源文件版本不变而目录归属、授权关系或目标映射变化，也必须让旧判断失效。
各事实分别新鲜不等于同时有效。执行 profile 必须提供一致快照、完整 read-set
的条件执行、固定关系，或用户明确允许的快照语义。仅靠 TTL 不满足实时一致性。

资源更新只替换有效证据/候选，保留消费和披露历史。Reserved 始终绑定原版本及
原精确请求，不能静默改成新版。GC 可删除大对象和无用候选，不能删除计数、
身份墓碑、未决执行、必要幂等索引及保密依赖。
未知/部分发现不证明“没有”“唯一”或“所有对象都处理完”；首版没有全集完成证明。

## 8. 独立披露状态机

`DisclosureSpec` 必须先于 projector 独立定义，不得等于“当前实现输出的字段集合”。
每条披露项描述接收者、固定函数和参数、输入依赖、输出有限类型/精度、合法时机、
次数上限，以及允许暴露的存在性、相等关系、状态和终止信息。
一次布尔观察可能泄露关键秘密；次数上限不是差分隐私或任意语义隐私保证。

### 8.1 两个明确的模式

**StrictPublicProgress（默认研究模式）**

- 对模型只返回公开提交回执和预定观察窗口信息，不返回资源/候选槽位。
- 默认不公开私密命中、业务余额、去重、PendingApproval、Unknown 或真实完成时刻。
- “窗口关闭”仅表示按公开期限停止接收新请求，不表示私密任务成功或全部完成。
- 详细结果由认证用户在私密 UI 查看。

**DeclaredFeedback（显式选择）**

- 可选择经审查的粗粒度函数，例如某步骤截至指定观察槽是否有已确认结果。
- 其真假、未就绪状态、关联性和对后续规划的影响都算明确允许披露。
- 若选择实际完成标志，其真假也必须列入规格；首版仍只在预定观察槽发布。
  事件即时推送不在首版内，未来启用还需明确批准事件存在性与时机的披露。
- 第一版禁止 arbitrary predicate/threshold/string summary；不自动把任何审批消息
  或错误详情当作公开反馈。

### 8.2 发布与观察的区别

发布机会由根契约中公开的逻辑槽/时间窗口或公开命令序号决定，不能由私密
候选变化、实际消费、内部 commit 次数决定。每个槽最多生成一份新观察记录。
隐私分支只 OfferObservation，不能在分支内触发一条额外公开消息。
若某槽是否有材料、是否完成本身未准披露，该槽的公开内容只能来自公共状态；
不能通过“暂无结果”与“有结果”的区别绕过检查。

公开槽在正常服务下不能因秘密不同而缺失：未来槽仅按公开日程返回统一的
`WindowNotOpen`；已到期槽的 Strict 记录只从公开提交/窗口状态构造，不依赖
私密证据、业务进度或其投影是否成功。Declared 模式的固定函数必须覆盖材料缺失、
失效、未就绪及私密检查拒绝；这些区别要么被明示批准，要么映射到同一个获准
结果，且其全部分支均须能合法通过释放门。不能在最后关头以“没有记录”绕开约束。
若无法证明某披露契约的全部分支可发布，任务接纳时拒绝该模式，不在运行时
用由秘密决定的空槽、错误或公共服务故障掩饰。私密诊断只能写入受保护记录。

对新 EvidenceCut 或新消费状态重新求值，即使字节与上次相同，也消耗一次观察槽。
只有再次读取同一份已冻结记录，且不重新检查秘密以宣称“当前仍然如此”，才是
不新增观察的重读。消息含公开槽标识和历史语义，不把旧记录冒充当前执行许可。

披露槽数、公开输入配额、公共缓冲空间在任务接纳时有界保留。槽耗尽按公开
日程停止新求值，不因私密信息刚好发生变化而额外发出 Unavailable。
私密执行/查询额度耗尽仅导致本地停止；若云端需要知道，须有相应披露项。

每次发送/重读仍验证当前接收者、会话、根阅读权限及已批准的历史阅读期限。
源事实后来变化不会改变已经合法释放的历史记录内容，也不能通过缓存校验
反向暴露新的源版本；新动作始终重新校验当前证据。用户撤销阅读的可观察行为
作为独立认证控制事件处理，来源撤销则不自动变为公开事件。

新观察按契约处理当时的证据有效性；已经合法释放的历史记录必须携带冻结的
历史释放依据，重读不重新访问源版本或源撤销表。若现有 declassification 接口
不能表达“当时合法释放、现在仍获准读该历史记录”，须新增独立受审查的证明
类型/版本后才启用该模式，不能绕过原门、延长过期父证据或默认为已经兼容。

阅读撤销和执行撤销分别处理。读取许可与 ReadRevoke 在同一 owner 下线性化：
撤销之后不产生新读取许可；撤销前已线性化的精确字节发送可以在短 lease 内
完成，不承诺远端在撤销后绝不再收到字节。每次历史重读仍需新的当前读取许可；
不新增观察槽不等于免认证。恢复不能用过期的旧发送许可重新发送。

## 9. 模型协议与公开错误

新模式的模型面只需要两个逻辑操作，最终 SDK/wire 版本另行审查：

```text
submit_step(task_handle, program_handle, public_args, command_id)
    -> AcceptedReceipt | PublicRejection

observe(task_handle, published_slot?)
    -> FrozenPublicRecord | PublicRejection
```

`AcceptedReceipt` 只表示一个有界提议已被可靠接收，不表示动作已授权、已执行或成功。
它的字段只依赖认证公共身份、规范化公开请求、公开窗口和 command_id。
重连沿用原任务和已持久化记录，不自动重新提交程序。取消/撤销通过现有认证控制面；
模型持有任务 handle 不等于有签发、扩权或重新认证权限。

`PublicRejection` 仅用于在读取秘密前即可判定的错误：格式、未授权角色、公开
程序/参数非法、公开提交配额/期限、相同 command_id 对应不同公开请求。
私密资格/额度/执行结果错误不能直接返回，即使所有私密错误使用同一错误码。

公开提交配额按新公开 command_id 单调收费，不按队列内剩余工作量或已完成项返还。
否则私密耗时和命中数会经 QueueFull/Busy 泄露。幂等键绑定主体、稳定任务、
规范化公开命令；相同命令返回同一接收回执，不附加私密“已完成/已消费”标记。
相同新请求不同 command_id 可接收为新提议，但业务消费域仍阻止重复执行。

接纳前按公开上界保留回执、观察记录和恢复元数据所需字节，计算范围包含共享
snapshot 的最大序列化体积、提交临时副本、必要日志、墓碑与幂等索引，而非仅给
内存队列设置长度。私密 facts/响应/审计有独立硬上限，不能占用公共保留区；其
回收也不返还新的公开提交机会。只读 poll 不无限追加持久审计，使用有界聚合计数。
若底层存储不能落实该隔离，容量泄漏保护属于未完成部署前提，不得宣称已经解决。

observe 不推进执行、刷新事实、重算资格、生成披露或提供私密 receipt existence oracle。
它只能读取本人本任务公开槽中已获准的历史记录；私密 reservation_id、ResourceKey、
证据哈希、内部 epoch 不可作为模型查询参数或响应字段。
模型侧 OpenClaw/Python 仅封装上述协议，不解析私密 data 或生成安全投影。

## 10. 持久化对象与两类提交流程

扩展现有 kerneld durable owner，不新增可独立派发的生产数据库。

| 持久对象 | 关键内容 |
| --- | --- |
| TaskRecord | 根契约、稳定 lineage、域定义、公开提交/披露槽、撤销和历史 |
| EvidenceIndex | ResourceKey、当前 facts/read-set、水位、标签、不可变私有对象引用 |
| PrivateContinuation | 程序身份、节点/私密 pc、循环游标、依赖、局部值引用、fuel、待审批/结果 |
| ConsumptionLedger | 稳定 ChargeKey、多级累计次数/量、墓碑、不可变 debit vector |
| ExecutionReservation | 精确动作/版本/见证/审批、原 nonce/期限、execd 关联及结果引用 |
| AdmissionRecord | 公开命令与幂等绑定、冻结接收回执；不混入内部状态 |
| ObservationReservation | 稳定槽、固定不可变状态切片、函数/参数/接收者/规格身份、一次性 debit |
| ObservationRecord | 稳定槽、接收者、精确输出、独立披露依据、状态切片、发布权限/额度 |

私密大对象使用既有 vault/retained-response，先持久保留对象，再提交引用；失败
可以留下孤儿，但不能公开引用尚未落盘的值。跨 owner 没有假想的统一数据库事务。

### 10.1 执行事务 T_exec

1. 幂等恢复已有请求则核对原不可变绑定，不重算额度或发行新许可。
2. 新预约重新校验完整动态 witness、EvidenceCut、当前授权/撤销、依赖和审批。
3. 原子检查全部稳定消费域，checked arithmetic 计算 debit vector。
4. 同时持久化额度消费、审批消费、Reserved 和精确 dispatch 绑定。
5. 持久化状态及外部锚确认后，才允许执行许可离开 owner。

首版动态路径从 Reserved 起永久消耗尝试/量，不自动退款或业务重试。
多条规则/多个请求同时争用一次资源机会，最多一个预约成功。
旧静态路径的既有 NoEffect 合同语义不在本提案中修改。

### 10.2 披露事务 T_release

披露是一个小状态机，而非一次可能被恢复重试的即时求值：

```text
Unused -> ObservationPinned -> FrozenRecord -> (短时读取许可) -> 发送/重读
```

1. T_pin：在公开观察槽，原子固定不可变状态切片、规格/函数/参数/接收者，消费
   该槽并保存 ObservationReservation。状态和锚确认后，才开始该逻辑观察。
2. 对固定切片运行纯、确定性、有界的 total 投影，不调用 provider/模型、不读取
   新的时钟、当前源状态或其他可变秘密。依赖对象在 reservation 存活时禁止 GC。
3. T_freeze：复核输出及控制依赖符合独立 DisclosureSpec 和现有释放规则，原子
   保存精确字节、冻结披露依据和原 release 关联，不再消费第二个观察槽。
4. owner 及锚确认后，取得当前精确读者的短时读取许可，经过 PlannerCall /
   BuildPlannerEnvelope 与 handoff，将记录交给对应接收者；禁止 Python 旁路 JSON。

恢复只允许针对原固定切片重做确定性计算，属于同一次逻辑观察；不能在同一
槽选更晚快照。如果需要观察新数据，必须使用下一合法槽。Strict 的槽不依赖
私密分支，Declared 的所有合法/缺失/拒绝输入必须具有第 8 节规定的 total 发布语义。
源撤销造成的私密检查结果不能让公开槽缺失；最终读者权限变化则按独立认证控制
事件及阅读线性化处理。任何具体释放门无法满足此契约时，阻止启用该模式。

输出不能因失败重建成不同请求/不同字节再沿用旧 release。提交后丢回复不返槽。
如果实际发送的完整 envelope 含其他私密内容或变化字段，也必须分别通过现有
释放门；不能仅验证 ObservationRecord 就宣称整个 prompt 合法。

执行结果先真实保留并提交，再允许发布声称该结果的观察。执行已提交而披露
失败时，执行事实和消费仍在，后续只处理原记录或下一合法槽，绝不再次执行来
“重建进度”。是否允许运行中的私密任务在披露停止后继续，由根契约确定。

## 11. 执行状态与恢复

内部状态采用既有执行路径的可对齐语义；以下不是新增 wire tags：

```text
Candidate -> PendingApproval -> Reserved -> AttemptFenced -> Retained -> Succeeded/Failed
                                               |
                                               +--------------------> Unknown
```

Candidate 可因事实更新失效并重派生；Reserved 及其消费不能回退到 Candidate。
终态分类依赖匹配原请求的保留响应，模型自报不推进状态。

| 故障切点 | 恢复行为 |
| --- | --- |
| 接收事务前 | 没有 Accepted；按原公开命令可重试接收 |
| 接收已提交，回执丢失 | 返回原接收回执，不重新插入私密工作 |
| 执行预约尚未提交 | 没有许可，不得发起外部执行 |
| Reserved，execd 认证日志证明未尝试 | 原请求/期限/前置条件仍有效时继续同一预约 |
| execd 可能已尝试但无保留响应 | Unknown；不重发、不退款、不换 executor/nonce |
| 真实响应已保留 | 重做本地分类/结果提交，不重做 provider 调用 |
| 私密终态已提交，披露未提交 | 保留终态，在合法槽处理披露；不能公开半成品 |
| ObservationPinned 后、FrozenRecord 前 | 同一固定切片重算，不换输入、不返槽，保留所有依赖 |
| 披露已提交，回复或 ACK 丢失 | 原冻结记录幂等重读，不新求值、不返槽 |
| anchor 已推进，文件缺失/落后 | 停止并报可信运维错误；禁止初始化空状态 |

kerneld 和 execd 均需防回滚与身份对账。仅保护 kerneld 计数无法防止旧执行器
日志下的再次尝试。续行游标、私密 pc、去重/披露索引也必须恢复，不能仅恢复 counters。
外部锚不能与同一份磁盘备份一起回滚；只保证已覆盖的恢复路径，不承诺任意宿主
管理员删除全部状态后仍可恢复。新安装身份不是旧任务恢复。

根撤销以 prepare 为线性化点：禁止新预约，已 Reserved 的动作可能在原 lease 内
继续；不承诺撤销之后物理世界绝无新效果。持续开销和后台队列亦受根期限约束。
所承诺的是受监控尝试次数和披露机会不再生，不是任意远端服务内部 exactly-once。

## 12. 最小区分案例与可用性要求

任务规则允许查询 A/B/C 命中的已验证文件归档，目标固定，业务总尝试预算 2，
每逻辑资源一次。两世界具有相同公开程序、提交顺序、预算上限和 StrictPublicProgress：

| 步骤 | 世界 W0 | 世界 W1 | 云端允许看到 |
| --- | --- | --- | --- |
| A 的结果 | F | F | 相同提交回执 |
| B 的结果 | F | G | 相同提交回执 |
| 本地执行 | F 一次；B 不新增机会 | F、G 各一次 | 相同公开窗口记录 |
| 私密剩余预算 | 1 | 0 | 不公开 |
| C 命中新的 H | 可消费一次处理 H | 额度不足，不执行 H | 相同接收回执，私密结果不同 |

例子不宣称预算不足的世界也完成 C。认证用户看到真实的已完成、已消费或额度
不足记录；云端窗口回执不冒充业务成功。若用户要求云端知道 C 是否成功，就
必须修改披露契约，使该区别明确可见，不能继续声称两世界不可区分。

加入 F 改名/版本变化、来源密钥轮换、并发 B 和崩溃，验证身份/消费连续性。
另设 DeclaredFeedback 任务，允许公开某种粗状态，使同一自适应模型确实能够
基于合法反馈选择不同的下一程序；不能仅用确定性脚本代替并宣称已证明模型收益。

文件归档与邮件添加固定标签使用同一 evaluator/ledger；身份、事实映射和请求
前置条件由各自受审查的 Rust 适配器提供。不能为每个例子写一个特殊内核分支。

## 13. 待证明的性质

这些是证明目标，不是当前实现已获得的定理。

**A. 派生动作可靠性**

每个 Reserved 动作都能由认证根规则和该 prepare 时刻有效的一致证据推导出完整
工具/效果/资源/目标/参数约束。根外动作不因事实新增而获得权限。

**B. 消费守恒**

在同一稳定任务/消费域中，累计 debit 不下降、不超过初始预算；版本、别名、
跨规则匹配、更新、恢复、重发及 GC 不建立新的额度。每个 observation 槽至多
绑定一个逻辑观察；对其固定不可变切片的恢复重算不构成新观察。安全迁移保留
这些量及等价类，不以重置命名空间替代迁移。

**C. 相对独立披露规格的交互隐私**

对同一自适应 planner、相同公开输入和相同公开基础设施可用性/故障日程，若
两世界独立理想披露状态机产生相同披露轨迹，则实际完整模型轨迹应同分布。
公共随机标识按公开发行位置耦合，随机源不能被私密执行次数推进；优先直接比较
完整序列化字节。必须重命名时，只能做全轨迹一致的一一映射，保留命名空间、
重复出现、相等关系和别名图；禁止把所有 handle 替换成同一个占位符再声称相同。
理想机器不能调用生产 projector；不得把实际输出或所有授权错误反过来定义为允许 L。

比较包含接收回执、公开错误、消息有无、逻辑发布槽、形状、相等关系、历史重读
与关闭语义。未处理的墙钟时间和物理资源侧信道不包含在该首版性质中。
单独的崩溃安全测试在每个内部提交切点注入故障；关系式测试使用与公开历史相容
的耦合故障日程，不能仅比较两个恰好走相同私密分支的运行。

**D. 恢复保持性质**

任意允许的 reopen 状态保留 A/B/C 所需的授权、消费、保密依赖与发布状态；
不得从执行不确定性制造一次新执行或一次未经计费的最新观察。

**E. 非平凡可用性**

在事实有效、审批满足、预算足够、适配器与调度可用的前提下，支持的有限程序
可以完成其合法动作；预算不足/Unknown 的限制如实报告给对应获准接收者。
不证明任意任务都可自动完成，不用全拒绝、假成功或任意宽披露满足安全测试。

## 15. 实施与验收顺序

首版工程上限候选：每根 16 个规则/8 个程序入口、每程序 64 个 AST 节点、循环嵌套
最多 2 层、一次发现最多 256 条/256 KiB、每任务最多 256 个历史资源身份、32 次
公开提交和 32 个新观察槽、每程序激活最多 10,000 个本地求值步骤。
这些是未测量的保守初值；查询尝试/字节/业务动作另设稳定预算，不能用 fuel 代替。
公开配额与私密工作空间分别有界预留，批次溢出私密停止，不返回依赖秘密的 Busy。

| 阶段 | 交付物 | 进入下一阶段的条件 |
| --- | --- | --- |
| P0 独立规格 | 契约/标签/观察机器、双世界与弱组合反例 | 能准确判定允许披露与成功，不依赖实现自证 |
| P1 纯检查器 | 有界 AST、字段用途、动态 witness、模型面类型 | 非法流、任意阈值、混证据/混规则全部拒绝 |
| P2 状态与发布 | 稳定消费域、公开 admission、T_exec/T_release | 并发与每个持久化切点故障验收 |
| P3 真实安全链路 | 既有审批、G1–G7、planner 释放、execd/vault 恢复 | 受控 provider 上真实调用计数、精确请求和保留结果 |
| P4 通用性/模型 loop | 文件、邮件共核；同一自适应 planner | 私密模式无多余关联泄露；允许反馈模式确有合法续行 |
| P5 研究与交付 | 强基线、消融、限制、迁移与冻结审查 | 实验真实可复现，再决定论文主张与部署 |

必须覆盖的负向/关系式测试：

- A/B 重叠与不重叠、私密余额不同但公开配额相同；C 在一边可执行一边不可执行。
- 同资源版本/路径/别名/密钥/connector 会话改变、多规则并发、ABA 与身份编号复用。
- 签名但攻击者可填的字段、源/目录关系变化、混快照、部分结果伪称完整。
- 公开入口不存在与私密候选不存在区分、重复 command_id、相同请求不同编号。
- 同字节新快照必须消耗新观察；冻结历史读取不新求值；poll 不刷新秘密。
- 私密业务额度/容量耗尽、异常、fuel、审批等待、提前完成不偷偷改变公开反馈。
- 有效输出、否定输出、无输出、epoch、排序、handle 相等、过期、重连全部纳入 transcript。
- 事实保留/接纳、prepare、attempt fence、结果保留、终态、观察 pin/freeze、发送/ACK 的故障切点。
- 两个 owner 的缺失/回滚/不确定提交、披露许可撤销、旧缓存不能绕过读者权限。
- 新旧协议交叉拒绝、迁移保留所有计数/墓碑/未决记录、降级不静默丢字段。

旧原型的 26 项测试、既有静态模型和生产回归不计为本设计的新验收。本轮未运行这些测试。

## 16. 研究定位、强基线与停止条件

截至本次核对，以下都是重要先例，不应将它们简化成“只做静态白名单”：

- [SecureClaw](https://arxiv.org/html/2606.09549v1)：已有私密 handle、受控摘要、
  精确执行绑定及重放保护。其拒绝后续行不应笼统当作磁盘回滚恢复保证。
- [CapLease](https://arxiv.org/html/2608.01710v1)：已有 token 无关的持久授权消费，
  包括重规划、并发、委派和崩溃；外部效果保证具有幂等接收端前提。
- [Agent libOS](https://github.com/yingqi-z20/Agent-libOS/blob/main/docs/data_flow.md)：
  当前文档已有数据放行、有限权限预约和待执行意图的同事务边界及不确定恢复。
- [SPA](https://arxiv.org/html/2608.27234v1)：已有计划优先的条件/循环执行和保留标签
  的跨查询私密状态复用，每查询只调用一次规划器。
- [去重侧信道先例](https://research.ibm.com/publications/side-channels-in-cloud-services-deduplication-in-cloud-storage)：
  “去重反馈可透露存在性”本身不是新的发现。

本方案的候选区别，是授权状态的可观察性与稳定消费在动态更新/恢复中的共同约束。
需要检验，不保证该区别已超越所有已有系统。

基线至少包括原项目、同样拥有本地分支和共享稳定账本的加强组合、给账本增加
普通 IFC 标签的强基线，以及纯本地固定工作流。不能故意让基线按临时 token
记账，再把它失败当作整个领域无法解决问题的证据。
先在小有界模型中找最强组合与新机制的可复现差异，再做实现和模型效用实验。
测量真实任务完成、重复/越界尝试、未经允许的区分、审批负担、恢复损失和系统开销。

以下情形应停止扩大研究主张并重新定位：

1. 强基线在同等契约/信任/披露边界下已满足全部性质，新增机制只有名称差异。
2. 隐私只能通过全拒绝、假报成功或允许泄露全部敏感分支得到。
3. 无法保持稳定资源身份，或执行前置条件不能由实际 profile 落实。
4. 自动化收益完全来自绕过既有审批，或秘密仍被传入 Python/云端处理。
5. 恢复只能依赖清空状态、换安装身份、重签授权或不受控的 provider 重试。

下一步如批准实现，先做 P0/P1 小范围规格与反例，不先改整套生产内核。
生产安装、迁移、外部账号操作、提交/push/PR 都需相应单独任务授权。
