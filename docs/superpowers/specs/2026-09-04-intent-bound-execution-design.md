## 2. 已核实的实现缺口

现有代码有精确动作绑定、值溯源、解密级、配额和执行日志基础，但不能视为本设计已经完成：

- `propose_tool_call` 当前向关系验证传入空集合，不能据此声称已执行用户级资源—目的地关系。
- 现有动作标识和绑定不是独立的用户任务授权状态机。
- `ControlEndorsement`、完备候选域和七控制选择尚未在该代码基线落地。
- 2026-09-03 设计允许签名开关放行 `ContextClean`，并允许部分 `OutsideIntent` 经动作审批继续。本研究的严格模型不采用这两条规则。
- 现有 worker 编码与 provider transport 需逐段审计；worker 的签名或消息长度正确不等于生成的请求符合已批准的动作。

## 3. 设计选择

选择在现有 Rust 内核、策略 WAL、执行器和审批通道中扩展，不创建平行的演示内核。

不选择仅靠每次人工审批：保留该产品策略作为可选的更严格限制，但它不能替代任务授权，也不能证明自动执行路径安全。

不选择把受信任的自然语言模型换成另一个模型：模型只能提议，不能提供授权事实。

首期采用受限、明确的授权语言及有限的请求编码配置。不承诺任意自然语言、任意 MCP 工具代码或第三方服务内部副作用的语义正确性。未支持的工具配置必须拒绝，不得回退到通用字节透传。

## 4. 安全边界

攻击者可控制 planner 输出、agentd 进程、工具结果及不可信编码 worker 的输出；知道全部策略。假设内核、授权签发器、可信审批渲染器、执行器中的受控请求编码/复核、OS 隔离和加密原语正确。

安全主张约束受监控出口的业务请求/动作尝试，而不是远端系统任意内部行为。远端实现符合公开接口语义是单独的契约假设。

不声称通用语义保密、时间侧信道防护、可用性或远端恰好一次。现有五个解密级转换及内容门职责不弱化。新增机制不能以严格拒绝为由绕过其他现有安全门。

## 5. 独立任务授权根

新增类型化任务授权对象，概念名 `TaskAuthorizationV2`，由内核侧专用用途签发者在 planner 执行前建立，绑定：

- 主体、任务、授权身份、版本、部署/策略身份和有效期；
- 完整的授权条款集合及其分组关系；
- 显式资源域、目的地域、允许的工具/效果、条件、次数和预算；
- 原始用户证据、规范化/渲染版本、证据来源与确认记录的摘要。

输入来源只有：认证的结构化输入；受限语法中明确识别的用户表达；由可信 UI 显示全部字段后得到的任务级批准。模型生成的草稿本身不是证据。

无法确定的表达不能默认获得 READ 所覆盖的所有资源；只能产生不执行的草稿，或已明确授权资源上的有限只读合同。副作用缺字段、代词指代不明和有歧义的表达进入任务级确认或拒绝。

首次实现以结构化输入和批准草稿为完整路径。确定性文本入口仅接受实现并测试过的闭合语法；不允许论文声称开放式文本自动编译。Python 可传递草稿和闭合状态，但不能签发授权、传入可信 evidence，或获得新增数据平面权限。

动作级审批只能从合同允许的候选中确定具体动作，不能加入合同外的效果、资源或目的地。确需扩权时，必须进行独立的任务授权修订，显式展示增量，携带既有消耗；不能把扩权伪装成普通动作审批。

## 6. 完整动作关系与受限任务状态机

七控制面保留为表达格式，不能独立求交后任意组合。定义完整业务动作 `ActionContentV2`，包括工具/编码配置、效果、资源、目的地、大小/数量等控制值、触发条件和 payload/溯源绑定。

授权条款同时匹配上述字段。例如允许 `(文件 A, Alice)` 和 `(文件 B, Bob)` 不允许推出 `(文件 A, Bob)`。

每个条款有稳定身份、前置条件、计数或有限预算和后继状态。最初支持闭合的合取谓词、显式值集合、整数界限及已验证完成证据；不引入任意脚本、模型解释或可执行策略回调。非法、溢出、缺失单位或未知操作符直接拒绝。

状态机允许合同内的动态计划，而不是把最初的模型计划当作授权根。重新规划不能改变合同、消耗记录或依赖条件。仍绑定每次评估使用的计划版本；版本变化需重新评估，但不能让旧证据获得新含义。

跨运行的额度按任务授权身份及条款记录，不能仅以请求 ID、步骤 ID 或执行 nonce 为键。自动开启新 run 不重新签发权限。用户显式开启的新任务属于新授权，而非暗中重置旧任务。

## 7. 选择、证据与完备候选域

每个 proposer 选择始终产生带 proposer 父节点的非权威记录，包括唯一候选和用户已指定值。选择的完整性均为 `ExternalUntrusted`，效果上限为 READ。上下文是否干净可用于审计，但不能产生授权捷径。

唯一的控制背书入口检查完整动作的匹配条款，并消费以下闭合证据之一：

1. 用户合同中的显式分组关系；
2. 完整授权候选域上的唯一性证明；
3. 对合同内具体动作的单次审批。

背书绑定动作内容、任务授权版本、条款、具体控制槽、候选域/状态版本和证据摘要，不能成为普通数据派生的父节点，也不能跨动作复用。

候选域首期只接受两种来源：合同中明确提交的有界完整集合；从已验证的完整活动注册表按合同确定性过滤的集合。运行时偶然发现的值、`prompt_values`、检索结果页或开放世界查询结果不能自动证明完整性。

记录候选域身份、范围、来源快照、集合摘要、成员及版本。成员资格和完整性是前提，唯一性是结论。新增、撤销、过期和相关注册表变更均重新验证；版本相同也不免除当前时刻的有效性检查。缺少完整性证据时只能在合同允许的范围内请求具体审批，不能放宽合同。

## 8. 无循环授权摘要

建立三个有严格构造先后的对象：

1. `ContentDigest`：规范动作内容、payload 及溯源、合同/条款、候选快照、评估前状态版本、描述和编码器身份。排除尚未生成的审批、背书和最终授权摘要。
2. 审批 settlement 与每个控制背书：分别绑定 `ContentDigest`，并绑定自身用途、主体、期限和各自证据；审批显示不能声称已存在尚未生成的背书。
3. `AuthorizationDigest`：`ContentDigest`、排序后的完整背书集合、所需审批、策略身份和状态转移绑定。capability、执行准备及后续回执使用它。

单独命名评估输入、展示摘要和授权摘要；禁止把含背书的最终摘要反向用于生成同一个背书。所有新摘要使用用途隔离和规范编码，明确字段及版本，不能仅更名旧函数而保留循环输入。

## 9. 持久化与并发

任务执行状态置于现有策略持久化快照/事务路径，不建立与策略 WAL 独立提交的第二份权限账本。

durable prepare 在同一原子提交中：复核合同/条款、当前状态、候选有效性及策略 fence；验证/消费 capability、背书和必需审批；占用任务额度及现有配额；记录唯一 execution nonce、封装引用和后继状态。只有提交成功才交给执行器。

内容门拒绝、复核失败或提交不确定均不得开始 provider 尝试。精确重放返回原记录，不重复消耗。新的请求编号若命中已耗尽的条款，拒绝。

`Indeterminate` 和 `EffectStarted` 保留相关消耗，不自动重试。证明无效果后的额度恢复必须是经过验证、持久化、只发生一次的状态转换，并受合同重试条件约束。依赖“执行已完成”的下一步必须等待验证过的完成证据，不能以 Prepared 充当完成。

复用现有部署 fence 与执行器 journal。撤销/切换不能回滚已发出的外部请求；相应主张应限定在实际检查/准备和受 fence 保护的边界，不声称瞬时撤销远端已发生效果。

## 10. 同一业务动作到实际请求

内核和执行器共享有界、类型化的业务请求表示及其规范编码规格，签名描述绑定受支持的编码配置及版本。

首期仅为现有传输支持的有限固定配置建立映射，例如有界 JSON-RPC `tools/call` 和受限固定方法/路径的 JSON 请求；具体工具资源语义仍需显式映射及人工审查。缺少映射的配置不能宣称已获语义约束，严格路径必须拒绝它。

可信执行器确定性产生请求，或对不可信 worker 的候选字节独立严格解析并复核等价性。未知/重复字段、控制字段别名、未经批准的请求方法/路径/工具/目的地变化和自动重定向拒绝；认证材料只能来自已绑定的凭据槽和目标身份。

内核先绑定业务请求及凭据身份，不能假称提前知道随后生成的时间戳认证头或 TLS 字节。执行器在添加受控认证材料后，复核业务语义未改变，将最终应用层请求摘要与 `AuthorizationDigest` 关联并持久化，再开放 provider 尝试。敏感材料不得出现在普通日志/Debug/论文轨迹中。

保证范围是经过监控的应用层请求，不包括 TLS 握手字节或恶意远端服务自行产生的额外行为。外部结果重新作为不可信数据进入内核。

## 11. 审批、协议与兼容性

可信展示包括合同/条款、工具、效果、资源—目的地对应关系、具体关键参数、次数/预算及条件。内容来自受控动作而非 agent 自述；正确转义、禁止控制字符混淆，超长拒绝而不是截掉授权关键字段。

新合同、动作内容和证据的 schema/摘要域显式版本化；不保留“缺新字段但仍自动允许”的旧构造路径。与权限相关的新字段禁止宽松默认值。需要协调 protocol、input-runtime、policy-core、kerneld、approvald、execd 和 SDK 的编解码及绑定检查。

V1 保持冻结。旧 V2 在途状态只能由明确版本的恢复器查询/核对，不能据缺失的新证据产生新的执行权限。已有外部效果和 Indeterminate 状态不能被丢弃；新任务需要新授权。无自动清库、重签旧审批或放宽启动检查。

SDK 是否新增方法由协议落点决定；不承诺“接口数量完全不变”。新增数据平面内容只走可信 ingress/approval 路径，不通过 JARVIS 内容无关的控制通道泄露。现有浏览器认证项目不作为本研究修改的附带目标。

## 12. 必须落地的集成点

| 组件 | 责任 |
| --- | --- |
| kernel-protocol / input-runtime | 有界规范类型、结构化/受限文本输入、授权证据来源及解析失败 |
| policy-core 的 labels/provenance | 不可信选择和受限控制背书；普通派生不可提权 |

| approvald / browser assets / SDK | 两类授权确认、可读且精确的展示、严格版本与错误处理 |
| execd 的 worker/provider 路径 | 受控请求编码及出口复核、最终请求摘要、故障与重放 |
| deployment assets / frozen manifest | 新 schema/信任用途检查与经审查的清单更新；不部署到本机 |

## 13. 验收标准

采用先失败后通过的针对性测试；不能用测试 helper 独有路径替代真实 daemon handler。完整验收至少包含：

- 摘要任务拒绝 send，即使目的地唯一、全局允许且收到动作审批。
- `(A, Alice)` / `(B, Bob)` 合同拒绝交叉配对；对应正确配对可以执行。
- 凭据齐全、类型正确的恶意 planner/agent 不能自报证据或绕过必需控制面。
- 换 nonce、重复步骤、重规划、并发 run 不突破任务次数/预算。
- 步骤条件、整数边界、单位、过期和授权修订按规则检查。
- agent 隐藏候选、分页只返回一项、候选失效或 epoch 改变不能制造自动背书。
- 无循环构造的摘要黄金向量，以及逐字段变更造成审批/背书失效的测试。
- 编码 worker 改写收件人/资源/工具/路径或插入重复控制字段，在 provider 调用计数增加前失败。
- 每个持久化边界的崩溃、精确重放、无效果恢复及未知结果测试；同时观测内核记录和出口尝试。
- 现有解密级、同源/会话、mTLS/角色、签名、隔离与配额检查没有绕过。
- 真实入口到受控 mock provider 的完整链路；真实服务接入只使用明确授权的测试资源。

建立有界状态模型覆盖合同、候选版本、审批/背书、准备、发送及恢复，核对模型事件和 Rust 轨迹。只报告实际检查的范围；有限状态探索不称为整个内核证明。

不因工程测试通过宣称攻击成功率、性能、任务完成率或论文接受概率已测得。
